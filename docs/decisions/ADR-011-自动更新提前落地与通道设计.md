# ADR-011 · 自动更新提前落地与 dev 通道设计

> 状态：Accepted · 决策日：2026-10-19 · 关联：M20 / UP1 / UP2 / UP3
> 影响范围：`apps/desktop/electron-builder.yml`（publish 配置）、`scripts/package-win.mjs`（版本注入）、`scripts/build-version.mjs`（新增）、`apps/desktop/src/main/update/`（新增）、IPC schema 新增 `update.*` 通道、设置页 UpdateTab 重写、新增运行时依赖 electron-updater
> 约束遵循：[新模块接入约束声明](../新模块接入约束声明.md)（全项通过）

## 决策

1. **UP1**：M20 Update Service 从 v0.3 计划**提前至 v0.1 开发期（dev.114）落地**，采用 **electron-updater ^6.8.9 + GitHub Releases dev 预发布通道**（`releaseType: prerelease`）。
2. **UP2**：版本盖章由**打包期从 CHANGELOG 派生**（`0.1.0-dev.NNN`），经 electron-builder `--config.extraMetadata.version` 注入安装包与 `app-update.yml`；`apps/desktop/package.json` 保持 `0.1.0` 不变。
3. **UP3**：发布纪律——每次 release **必须同时上传 exe + blockmap + dev.yml**；`--publish never` 只生成本地更新清单，上传保持人工 `gh release` 门禁。

## 背景

用户在实际使用 dev.112 后提出：设置页「更新」目前只是说明占位，新版本发布后每次都要手动下载约 363MB 安装包重装；要求本地有新版本时，设置页更新按钮可以真正检测、下载并安装。

既有约束：

- NFR-REL-05 原计划 v0.3+ 提供自动更新能力；M20 在 [04-模块全景](../04-模块全景.md) 登记为 v0.3+。
- CON-07 决定首版**无代码签名**（Windows 安装包未签名）。
- AGENTS.md 项目声明：生产级标准自 v0.1 起全程适用；新模块接入须遵循 [新模块接入约束声明](../新模块接入约束声明.md)。

## 候选方案评估

### 候选 A：electron-updater（选定）

与 electron-builder 同生态（electron-userland 官方维护），直接消费本仓库已有的 NSIS + blockmap 产物；GitHub provider 免自建后端；支持 channel 与 prerelease 语义；纯 JS 依赖，可在主进程懒加载，符合进程隔离与启动性能约束。

已知限制（源码核实）：electron-updater 6.8.9 的 GitHubProvider 只挑选 channel 匹配的**最新** release；若最新 release 缺少 `dev.yml`，更新器报 `CHANNEL_FILE_NOT_FOUND` 且**不会回退**更旧 release——以发布纪律（UP3）与 release 验收清单兜底。

### 候选 B：自研更新器（否决）

需自行实现 release 元数据解析、sha512 校验、NSIS 静默安装参数、原子替换与回滚；实现与维护成本高、缺陷面大，且无法天然复用 electron-builder 的 blockmap 增量信息。收益仅是少一个 MIT 依赖。

### 候选 C：推迟到 v0.3（否决）

用户当前每个 dev 版本都需手动重装约 363MB，痛点已实际发生；推迟意味着后续所有 dev 交付持续付出人工安装成本，与「小步快跑」冲突。

### 候选 D：第三方托管更新服务（如 update.electronjs.org）（否决）

平台按 stable/latest 语义分发，不支持 dev prerelease 通道与自定义 channel 文件；引入外部服务可用性依赖，且不匹配本仓库既有 GitHub Releases 发布流程。

## 决策理由（方案 A）

1. **与打包链零冲突**：electron-builder 已产出 NSIS + blockmap，补 publish 配置即可本地生成 `dev.yml` / 包内 `resources/app-update.yml`。
2. **安全边界清晰**：更新器只在主进程运行（懒加载），渲染进程仅经 IPC 读状态、发指令；下载/安装路径与参数不外泄。
3. **手动确认制**：`autoDownload=false`，用户明确点击才下载与安装；检查不静默打扰。
4. **可测试性**：UpdateService 全依赖注入（currentVersion / isPackaged / notify / createUpdater），单测不触碰真实网络与 updater。
5. **通道隔离**：渠道名由版本 prerelease 段自动派生（app-builder-lib `appInfo.js` channel = 版本 prerelease 首段），dev 预发布与未来 stable 通道天然分离。
6. **版本可追溯**：安装包版本与 CHANGELOG 行一一对应（UP2），避免「同名不同版」包。

## 否决方案理由汇总

- **B（自研）**：实现/维护/安全校验成本高，仅为省去一个 MIT 依赖。
- **C（推迟 v0.3）**：用户每次 363MB 重装的现实痛点不解决。
- **D（第三方托管）**：不支持 prerelease dev 通道，增加外部依赖。

## 后果

### 正面

- 用户自 dev.114 起可在设置页一键完成「检查 → 下载 → 重启安装」。
- 发布仍保持人工门禁（`gh release` 手动上传三资产），符合 AGENTS.md §九「不可逆操作审批」。
- 无新增原生依赖；electron-updater 在主进程懒加载（独立 chunk），不增加启动开销。

### 负面 / 风险

- **引导期**：dev.113 及更早安装包不含更新代码，用户必须手动安装 dev.114 一次后才能进入自动更新链。
- **无签名（CON-07）**：NSIS 更新链校验 `dev.yml` 的 sha512，但不校验 Authenticode；NFR-REL-05 的「签名完整性校验」部分暂未满足，随代码签名在 v0.4 处理。
- **单一分发源**：release 缺 `dev.yml` 会导致更新器报错且不跳旧版本。

### 缓解

- 发布纪律写入 `electron-builder.yml` 注释与本 ADR；每次 release 后复核三资产齐全。
- 更新失败（网络/元数据异常）只回报 error 状态，不阻塞浏览器核心路径。
- 版本盖章门禁：CHANGELOG 缺失或版本非法时打包直接失败，杜绝错误版本流出。
