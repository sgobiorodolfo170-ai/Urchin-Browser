# 浏览器数据导入评估

> 状态：评估文档（dev.121，2026-10-25）
> 关联决策：[IM1 书签导入策略](./decisions/决策索引.md) / [IM2 站内数据导入评估结论](./decisions/决策索引.md)
> 关联功能：设置页「通用 → 从其他浏览器导入」（dev.121，仅书签已实现）

## 1. 范围与原则

本文档评估「从其他浏览器导入站内数据」的可行性，覆盖：**书签（已实现）/ Cookie / localStorage / IndexedDB / Service Worker / 缓存**。

通用原则（适用于所有数据类型）：

1. **同机同用户**：导入仅在同一 Windows 用户、同一台机器内进行——Cookie/Storage 的加密密钥与 Windows 用户数据保护（DPAPI）绑定，跨用户/跨机不可解密。
2. **源浏览器需关闭**：Firefox 运行时对 `places.sqlite` 持有排它锁；Chromium 系运行时对 Cookies/Storage 加锁。导入前提示用户关闭源浏览器，或采用「复制临时文件再只读解析」策略（本项目 Firefox 导入即用此法）。
3. **导入前确认 + 进度 + 可中断**：长操作必须显示进度并允许取消；失败不阻塞浏览器启动。
4. **失败不破坏现有数据**：导入是「增量写入」——新建独立文件夹（书签）或 `session.cookies.set`（Cookie），不覆盖 Urchin 既有数据；不满意可删除导入的文件夹。
5. **隐私**：导入路径仅记 basename + 计数；URL/Cookie 内容不进日志（与 files 域约定一致）。
6. **加密凭据不导入**：密码/自动填充/支付卡等涉及操作系统密钥保险库（Windows Credential Manager / Chromium safeStorage）的数据**不在评估范围**——其加密密钥无法跨浏览器复用，强行迁移会破坏密钥链。

## 2. 各数据类型评估

### 2.1 书签（已实现 · dev.121）

- **来源**：Netscape 书签 HTML 文件（Chrome/Edge/Firefox 通用导出格式）+ Chrome/Edge `Bookmarks` JSON + Firefox `places.sqlite`。
- **可行性**：高。三种格式均为标准/可解析结构，无加密。
- **实现**：`src/main/import/` 模块，3 个 IPC 通道（detectBrowsers / bookmarksFromFile / bookmarksFromBrowser），导入到「导入自 \<浏览器\> (日期)」文件夹保留结构。
- **决策**：IM1（独立文件夹保留结构，不去重；否决：URL 去重合并——不可整体撤销）。

### 2.2 Cookie

**存储格式**：
- Chromium 系（Chrome/Edge）：`<UserData>\<Profile>\Network\Cookies`（SQLite），加密。
  - 主密钥：`<UserData>\Local State` JSON 的 `os_crypt.encrypted_key`，Base64 + DPAPI 前缀 `DPAPI` 解。
  - Chrome 80+：每 cookie 用 AES-256-GCM（v10 前缀），密钥来自 DPAPI 解出的主密钥。
  - **Chrome 127+ App-Bound Encryption (v20)**：主密钥额外由系统级 `GoogleChromeElevationService` 包装，需以 SYSTEM/浏览器进程身份才能解——第三方应用**无法**直接解 v20 cookie（除非该 Chrome 未启用 ABE 或仍存 v10 旧 cookie）。
  - Edge：与 Chrome 同源格式，但截至评估时未启用 ABE（DPAPI 可解）。
- Firefox：`<Profile>\cookies.sqlite`，`moz_cookies` 表，**明文**存储（无加密）。

**解密路径（Chromium，非 ABE 场景）**：
1. 读 `Local State` → 取 `os_crypt.encrypted_key` → 去 `DPAPI` 前缀 → DPAPI `CryptUnprotectData` 解出主密钥（Electron 主进程在 Windows 用户态可直接调用 `node:crypto` + 系统调用，或复用 Electron 的 `safeStorage` 间接验证）。
2. 对每条 cookie 的 `encrypted_value`（v10 前缀 + nonce + ciphertext + GCM tag）→ AES-256-GCM 解密。
3. 解出的明文 cookie 经 `session.cookies.set({ url, name, value, domain, path, expirationDate, secure, httpOnly, sameSite })` 写入 Urchin（Electron 自身的 session.cookies API，会以 Urchin 自己的 safeStorage 重新加密落盘）。

**可行性**：中-高。
- Edge / Firefox：可行（DPAPI 可解 / 明文）。
- Chrome（启用 ABE 后）：**不可行**——无法解 v20 cookie。建议：检测到 ABE 时提示用户「Chrome 已启用应用级加密，无法导入 Cookie，请改用 Edge 或导出 Cookie 扩展」。
- 工程量：中等（DPAPI 调用 + AES-GCM 解密 + 批量 cookies.set；需限流避免主进程阻塞）。

**建议阶段**：P1（在书签导入之后，作为第二期数据导入能力；先支持 Edge/Firefox，Chrome 视 ABE 实测降级提示）。

### 2.3 localStorage

**存储格式**：
- Chromium：`<Profile>\Local Storage\leveldb\*.ldb`（LevelDB），key 为 origin+key 复合，value 为 UTF-8/UTF-16 字符串。格式跨 Chromium 版本相对稳定（LevelDB 块格式），但 v9+ 有「live metadata」变更风险。
- Firefox：`<Profile>\storage\default\<origin>\ls\*.sqlite`（新版用 sqlite；旧版 `webappsstore.sqlite`）。

**迁移路径（两条候选）**：
- **方案 A（推荐）**：用 LevelDB reader（如 `classic-level` / `level` npm 包，或自研只读 .ldb 块解析）读出 origin→key→value，然后对每个 origin 在隐藏 BrowserView 加载 `about:blank` 后 `executeJavaScript(\`localStorage.setItem(k,v)\`)` 回放写入。**优点**：跨 Chromium 版本兼容（走标准 API）；**缺点**：每 origin 一次加载，慢；origin 列表需先聚合。
- **方案 B（不推荐）**：直接拷贝 `.ldb` 文件到 Urchin profile 的 `Local Storage\leveldb\`。**风险**：Chromium 大版本间的 LevelDB 元数据/compaction 状态不兼容，可能损坏 Urchin 既有 localStorage 或被 Chromium 启动时判废重建。

**可行性**：中（方案 A 工程量中等，需新增 LevelDB 依赖；方案 B 风险高不建议）。

**建议阶段**：P2（依赖 LevelDB 读库引入评估；v0.3+ 评估）。

### 2.4 IndexedDB

**存储格式**：
- Chromium：`<Profile>\IndexedDB\<origin>.leveldb\`（目录，含多个 LevelDB 文件 + blob 文件）。
- Firefox：`<Profile>\storage\default\<origin>\idb\`（类似结构，sqlite-backed）。

**迁移路径**：
- Chromium 同大版本：理论上直接拷贝目录到 Urchin profile 同位置可工作（schema 兼容时）。但 IndexedDB 的 internal schema 随 Chromium 升级有 breaking change 历史，跨版本拷贝有损坏风险。
- 跨浏览器/跨版本：需逐 origin 用 `indexedDB.open` + 遍历 objectStore + 逐条 `put` 重放——工程量大，且 blob/File 结构需额外处理。

**可行性**：低-中（同版本目录拷贝可行但脆；跨版本重放工程量高）。

**建议阶段**：P3（实验性，默认不导入；站点下次访问自动重建 IndexedDB 数据，多数 Web 应用可自愈）。

### 2.5 Service Worker

**存储格式**：
- Chromium：`<Profile>\Service Worker\Database.txt`（注册表 LevelDB）+ `ScriptCache\`（脚本缓存）+ `CacheStorage`。
- Firefox：`<Profile>\storage\default\<origin>\+sw`（注册）+ `+sw^…`（脚本）。

**迁移路径**：直接拷贝注册表与脚本缓存。但 SW 注册与脚本 URL 强绑定，且脚本缓存是按 origin 的 hash 寻址——跨 profile 拷贝后 Chromium 会在下次 SW 事件时校验脚本完整性，不匹配则自动注销重注册。

**可行性**：低（拷贝易，但命中率低，常被自动失效）。

**建议**：**不导入**。站点下次访问会自动重注册 SW 并重建缓存——这是浏览器标准行为，导入 SW 没有用户可见价值且有风险。在评估结论中明确「不实现」。

### 2.6 缓存（HTTP Cache）

**存储格式**：
- Chromium：`<Profile>\Cache\Cache_Data\`（Simple Cache 格式，版本相关）。
- Firefox：`<Profile>\cache2\entries\`。

**迁移路径**：理论上可拷贝。但：
- 缓存格式随 Chromium 版本变化（Simple Cache v1/v2），跨版本拷贝会被判废重建。
- 收益极低：缓存命中只是省一次网络请求，浏览器会自行重新填充缓存。
- 迁移大量小文件 I/O 开销大，价值不匹配。

**可行性**：低价值。

**建议**：**不导入**。结论明确「不实现」。

## 3. 结论矩阵

| 数据类型 | 可行性 | 风险 | 依赖 | 工程量 | 建议阶段 |
|---|---|---|---|---|---|
| 书签 | 高 | 低 | 无 | 已完成（dev.121） | ✅ 已实现 |
| Cookie（Edge/Firefox） | 中-高 | 中（DPAPI + ABE 检测） | 无（系统 API） | 中 | P1 |
| Cookie（Chrome ABE） | 低 | 高（无法解 v20） | — | — | ❌ 不实现（降级提示） |
| localStorage | 中 | 中（LevelDB 读 + 隐藏 view 回放） | LevelDB reader | 中 | P2（v0.3+ 评估） |
| IndexedDB | 低-中 | 高（跨版本 schema drift） | — | 高 | P3 实验性，默认关 |
| Service Worker | 低 | 中（拷贝易失效） | — | 低 | ❌ 不实现（站点自重注册） |
| 缓存 | 低价值 | 中（版本相关） | — | 中 | ❌ 不实现（无用户价值） |
| 密码/自动填充/支付卡 | 不可行 | — | — | — | ❌ 不在范围（密钥不可迁移） |

## 4. 实施路线（建议）

- **P0（已交付 dev.121）**：书签导入（HTML + Chrome/Edge/Firefox profile 自动检测）。
- **P1（建议 v0.2.x）**：Cookie 导入——支持 Edge + Firefox（DPAPI 解 / 明文），Chrome 检测到 ABE 时降级提示。设置页「数据导入」区块增加 Cookie 选项 + 进度 + 源浏览器关闭提示。
- **P2（v0.3+ 评估）**：localStorage 导入——评估引入 LevelDB reader 依赖（优先 `level` 轻量包），隐藏 BrowserView 回放方案原型验证。
- **P3（实验，默认关）**：IndexedDB 同版本目录拷贝——加实验开关，不在主流程暴露。
- **不实现**：Service Worker / 缓存 / 密码/自动填充/支付卡——在文档与 UI 中明示「站点自动重建」或「安全限制不可迁移」。

## 5. 安全注意事项

- **DPAPI 调用**：仅 Windows 用户态可解——本应用以当前用户身份运行，合规；不涉及跨用户提权。
- **ABE 检测**：Chrome 127+ 启用后，导入 Cookie 必须先检测 `Local State` 是否含 ABE 标记，是则拒绝并提示，避免误导用户「导入成功但实为空/旧数据」。
- **沙箱隔离**：所有解密在主进程完成（不进渲染进程 / 不进第三方代码），明文 cookie 不落日志，写入后即释放。
- **权限最小化**：导入模块不申请文件系统越权——仅读用户目录下已知路径，不写源浏览器任何文件（Firefox 复制到 temp 后只读，原文件不动）。
