# ADR-012 · 发布通道与版本号治理

> 状态：Accepted · 决策日：2026-10-20 · 关联：M20 / UP1-UP3 / RC1-RC3
> 影响范围：`scripts/build-version.mjs`、`scripts/package-win.mjs`、`apps/desktop/electron-builder.yml`、`apps/desktop/src/main/update/update-service.ts`、README / 路线图 / 技术栈 / 决策索引
> 约束遵循：[新模块接入约束声明](../新模块接入约束声明.md)（发布治理为既有 M20 的补充，不新增模块）

## 决策

1. **RC1 · 双通道、单版本线**：dev 预发布为 `X.Y.0-dev.NNN`，发布为 GitHub Pre-release + `dev.yml`；正式版为 `X.Y.0`，发布为 GitHub Latest + `latest.yml`。两者共用一条 SemVer 版本线，stable 只承载正式版，dev 只承载预发布。
2. **RC2 · 基线前进 + 全局计数器**：dev 基础版本必须严格大于 CHANGELOG 最近 stable；v0.2.0 发布后下一 dev 为 `0.3.0-dev.116`。`NNN` 全局递增、不按基线重置；`build-version.mjs` 在打包期执行门禁，低于/等于 stable 直接失败。
3. **RC3 · dev → stable 两段检查**：dev 版本先查 dev 通道，确认无更新后再切 `latest` 查稳定版；stable 版本只查 `latest`。首个 stable 发布前 `/releases/latest` 404 静默视为“暂无 stable”；每次切通道后强制 `allowDowngrade=false`。

## 背景

dev.114 已把 electron-updater 接到设置页，但版本语义存在两个未决问题：

- CHANGELOG 已记录 v0.1.0 为已发布版本，而 dev 仍使用 `0.1.0-dev.NNN`——SemVer 上 dev 低于 stable，首个 stable 一旦发布，所有 dev 安装都会被判定“更旧”。
- GitHub 的 Latest 只认非预发布版本；当前只有 dev Pre-release，`/releases/latest` 404，首页没有 Latest 卡片。

用户已确认：首个 stable 等 v0.2.0 验收通过；dev 计数器全局递增；允许 dev 用户升级到 stable。

## 源码核实（electron-updater 6.8.9）

`GitHubProvider.getLatestVersion()` 在 `allowPrerelease=true` 时的通道选择：

```js
const currentChannel =
  this.updater.channel || semver.prerelease(this.updater.currentVersion)?.[0] || null;
```

随后遍历 releases Atom feed，只接受 `hrefChannel === currentChannel` 的 tag。`channel="dev"` 时 stable tag（无预发布段）被跳过。因此：

- stable release 额外附带 `dev.yml` **不能**让 dev 用户选中 stable；
- 正确路径是两段检查：dev 无更新 → `allowPrerelease=false` + `channel="latest"` 再查；
- `AppUpdater` 的 `channel` setter 会自动把 `allowDowngrade` 置 `true`，必须显式设回 `false`；
- `checkForUpdates()` 无更新时返回 `{ isUpdateAvailable: false, updateInfo }` 而非 `null`——调用方必须以 `isUpdateAvailable` 判定。

## 候选方案评估

### 候选 A：双通道 + 两段检查（选定）

- dev 保留预发布通道与快速迭代节奏；stable 走 GitHub Latest；
- 版本线连续，`0.2.0-dev.115 < 0.2.0 < 0.3.0-dev.116`，semver 比较天然正确；
- 不新增服务、不改变现有 GitHub Releases 流程。

### 候选 B：stable release 同时上传 dev.yml（否决）

GitHubProvider 在 dev 通道下不会选 stable tag，`dev.yml` 放在 stable release 里不会被读取；发布资产还会混淆“当前 release 属于哪个通道”。否决。

### 候选 C：dev 与 stable 使用两条独立版本线/仓库（否决）

需要维护两套版本号与发布流水线，且跨线比较仍需人工映射；当前单产品、单仓库规模不需要。

### 候选 D：dev 计数器按基线重置（否决）

`0.2.0-dev.1` 会与历史 `0.1.0-dev.114` 失去单调性，回退/比较与发布记录都更易出错；全局递增更简单可审计。

### 候选 E：只发 stable，不再发 dev（否决）

dev 系列是当前主要交付节奏；取消预发布会让每次验证都占用正式版本号，违背“小步快跑”。

## 决策理由

1. **语义正确**：stable 是 dev 的后继而非平行分支，SemVer 比较与用户预期一致。
2. **渠道隔离**：dev 用户优先拿到 dev 更新；只有 dev 无更新时才提示 stable，避免 dev 用户被意外拉回旧稳定版。
3. **发布可验证**：`build-version` 同时派生 channel/releaseType，`package-win` 打包后校验 yml 与 `app-update.yml`，把“通道配错”变成打包失败而非线上事故。
4. **迁移可审计**：v0.1.0 仅作为 CHANGELOG 里程碑，不补发 GitHub release；首个 GitHub stable 为 v0.2.0，避免用当前代码伪造历史版本。

## 后果

### 正面

- GitHub 首次出现 Latest 后，普通用户有稳定的下载入口；dev 用户仍可继续使用预发布。
- 版本号与通道由同一份 CHANGELOG 行派生，打包与运行时不再各自硬编码。
- dev→stable 迁移路径明确，且不会把 `0.3.0-dev.x` 降级到 `0.2.0`。

### 负面 / 风险

- **桥接版本**：dev.114 及更早没有 stable fallback，无法自动迁移到 v0.2.0；必须先发布并安装 dev.115。
- **两段请求**：dev 无更新时会多一次 `/releases/latest` 请求；首个 stable 前该请求 404，需抑制 error 事件。
- **stable 不带 dev.yml**：只影响 dev 通道的发布资产检查；stable 用户不需要 dev.yml。
- **无代码签名（CON-07）**：仍依赖 yml 内 sha512 + blockmap 校验，Authenticode 校验留 v0.4。

### 缓解

- dev.115 先于 v0.2.0 发布，并在 v0.3 验收中记录真实升级链。
- stable fallback 的 404 以 info 日志记录，不进入 error 状态；单测覆盖。
- 发布清单固定为：dev = exe + blockmap + dev.yml；stable = exe + blockmap + latest.yml。
- 每次 release 后核对 `/releases/latest`（stable）或 Pre-release 标记（dev）。

## 发布流程

| 通道 | 版本形态 | 打包命令 | 产物清单 | GitHub 标记 | 运行时检查 |
|---|---|---|---|---|---|
| dev | `X.Y.0-dev.NNN` | `pnpm package:win` | exe + blockmap + dev.yml | Pre-release | dev.yml，失败后 latest.yml |
| stable | `X.Y.0` | `pnpm package:win` | exe + blockmap + latest.yml | Latest | latest.yml |

1. 在 CHANGELOG 表尾追加版本行（stable 需先完成版本验收）。
2. `pnpm verify` + `pnpm e2e`；打包后由 `package-win.mjs` 校验通道与资产。
3. 人工确认后 `gh release create v<version> <assets> --prerelease`（dev）或 `--latest`（stable）。
4. `gh release view` + 下载 URL 验证；dev 安装后检查设置页“已是最新/可更新”状态。
