# 构建、启动与退出卡死排查（2026-11-14）

## 已确认的原因

- 本轮卡死样本 PID 27312（独立速记验收实例）：CDB 非侵入线程快照显示 `CrBrowserMain → USER32/MSCTF → sogoutsf → SogouPy!ImeProcessKey → WaitForSingleObjectEx`，主线程被本机搜狗拼音组件阻塞。不是 UI 渲染的 JavaScript 死循环。启动打点显示该实例首载约 977ms，卡死发生在后续键盘交互。
- E2E 残留样本 PID 36348、32912：主线程栈为 `ExitProcess → LdrShutdownProcess → SogouPy → WaitForSingleObjectEx`。功能断言已完成，但原生 DLL 的退出卸载未返回，`electronApp.close()` 和 worker teardown 随之超时。旧输入法来自本机 SogouInput/8.3.0.9576 目录。
- 前几轮验收反复创建不同隔离档案；旧测试的异常路径也未完整回收 Electron，导致实例累计。单实例锁以 userData 隔离，不能阻止不同档案各启动一个进程。
- 启动脚本在 spawn 后立即报告成功，未检查子进程提前退出或主窗口是否就绪。品牌 exe 被占用时，重建相同图标仍可能因文件时间变化触发覆盖，出现 EBUSY 和 exe 回退噪音。

证据文件位于仓库本机忽略日志 `freeze-stacks.log`、`e2e-freeze-stack.log`、`microsoft-native-stack.log`。进程清单保留于系统临时目录 `urchin-process-audit-20261114.json`；这些本机诊断不提交源码库。

## 修复

1. `pnpm start` 等待主窗口回执；提前退出或 30 秒内未就绪则报错，并只回收本次创建的进程。心跳刷新停顿可识别“PID 存在但事件循环不可用”。回执不等同于全部网络服务就绪。
2. 新增 `pnpm start:review`：每个仓库使用固定的双目录隔离验收档案，活跃实例复用；发现其心跳过期则停止重复启动并提示排查。该命令不关闭日常安装版。
3. 全部直接启动 Electron 的 E2E 接入统一应用生命周期，包含初始化失败、断言失败、显式 close 和 fixture teardown 的回收路径。关闭超时可按本测试记录的 PID 外部回收，不按进程映像名批量终止。
4. 仅显式启用 `URCHIN_NATIVE_EXIT_GUARD=1` 且同时设置 `URCHIN_TEST_USER_DATA`、`URCHIN_TEST_DATA_DIR` 的 Windows 隔离实例：在既有资源清理完成后直接终止自身，绕开第三方 DLL detach。验收命令和 E2E 启用该模式。安装版和普通 `pnpm start` 默认行为不变。
5. 品牌 exe 缓存增加图标内容指纹；生成使用临时文件后再替换。被占用时保留已有可用副本，避免删除正在使用的 exe。

## 本机处理与边界

已取得用户明确授权，临时将输入法切至微软拼音，并重启本轮卡死的开发实例；不卸载搜狗，不操作日常安装版数据。搜狗 DLL 自身的等待无法由 JavaScript 解锁：测试退出兼容模式解决其影响验收的问题，但不声称修复第三方二进制。日常继续使用旧搜狗时仍可能触发输入阻塞，建议由用户更新／修复输入法，或继续使用系统输入法。

输入法默认设置的原值已保存在系统临时目录 `urchin-ime-before-audit.json`。初始切换为临时排障措施；用户随后明确选择保留微软拼音作为默认。进一步的 Windows 注册表／进程事件跟踪确认：`SogouSvc.exe` 启动 `SGTool.exe`，后者在约 1 秒内将 `InputMethodOverride` 写回搜狗；仅调用系统切换接口不能持久生效。

用户另行明确授权禁用该服务后，已将 `SogouSvc` 从自动启动改为禁用并停止，再设置微软拼音。多次间隔读取确认服务为 `Disabled / Stopped`，默认输入法保持微软拼音。服务原配置保存在系统临时目录 `urchin-sogou-service-before.json`，跟踪证据为 `urchin-ime-writer-audit.etl`／`.xml`。未卸载搜狗；禁用服务可能影响其后台功能。这是本机用户选择，不作为仓库对所有用户的全局配置。如以后需要恢复服务，可执行 `Set-Service -Name SogouSvc -StartupType Automatic`，并自行选择默认输入法。
