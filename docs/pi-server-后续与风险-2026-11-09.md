## 3. 关键风险点

> 每条都写「怎么发现 / 会怎么坏 / 现在有什么缓解」。**风险不是待办**——不要为了关掉风险条目而做无关重构。

### R1（高）shim 与上游版本漂移

- **是什么**：`packages/pi-web-host/src/pi-shims-{coding-agent,tui,mcp}.d.ts` 是**手写**的 ambient 声明。形状抄自 `vendor/pi/packages/*/src`，并与 `vendor/pi/packages/coding-agent/node_modules/@earendil-works/*/dist/*.d.ts`（1.4.0 同版）交叉核对过。它们不会自动跟随上游。
- **会怎么坏**：升级 `vendor/pi` 后，shim 可能「编译通过但字段已改名/变必填」——类型检查给出虚假安全感，运行期才炸。
- **怎么发现**：升级 `vendor/pi` 时，diff 新版 `node_modules/@earendil-works/*/dist/*.d.ts` 与 shim；重点看 `ToolDefinition`、`AgentSession`、`SessionManager`、`ModelRuntime`、`ExtensionUIContext`。
- **现有缓解**：`pnpm check:dsh` 只覆盖 DeepSeek Harness（G17），**不覆盖 pi**；shim 文件头的「形状来源（逐字核对，勿凭记忆改）」注释即契约。没有自动门禁——这是已知缺口。

### R2（中高）shim 里的 `any` 边界仍然存在

- **是什么**：`ModelRuntime` 仍有 legacy `src/pi-shims.d.ts` 的 `[key: string]: any`；`ToolDefinition` 的 `TParams` 默认 `any`；`ExtensionAPI.on` 的事件载荷是 `any`；`pi-tui` 的 `Component` / `Overlay*` 是索引签名。
- **会怎么坏**：这些边界上的错误仍然抓不到（例如把 `ctx.something` 拼错）。
- **现有缓解**：本次把工具链上最关键的 40 个导出精确化了；`pi-server` 的 412 条里约 390 条属 shim 连锁，已全部消除。**不要**为了让某条错误消失而把已知字段再改成 `any`。

### R3（已解除 2026-11-09）`declaration: false` 曾是检查口径的偏离

- **原状**：`tsconfig.pi-server.json` 关掉了 `declaration` / `declarationMap`（该程序只跑 `--noEmit`），
  因此不做声明可移植性检查（TS2742/TS4023），并把 3 条 device-center 的 TS2742 留在门外。
- **现在**：pi-server 已并回主 `tsconfig.json`（`declaration: true`），3 个导出函数补了显式
  `: Express` 返回类型后主程序 0 错误——**声明可移植性重新被检查**。专项程序里的
  `declaration: false` 只剩「省掉不产出声明时的多余检查」这一个作用，不再掩盖问题。

### R4（中）上游同源代码被本地修改

- **是什么**：`src/pi-server` 是 pi-web-ui（MIT）的同源移植。本次删了约 240 行（B4 死分支）、改了 3 处类型面（`plugin-assets.ts`、`device-center/device-lan.ts`、`provider-oauth-flow.ts`），并新增 `src/plugin-sdk/index.d.ts`（上游逐字副本）。
- **会怎么坏**：将来从上游整份覆盖升级会冲突；若有人「凭记忆重写」被删的 claude/codex/agy 绑定，会写错。
- **恢复路径**：`git show a5acce25:...`（terminals/index）、`git show c6538db6:...`（native-cli-session）或上游同名文件。提交信息里已写明。
- **缓解**：`plugin-sdk/index.d.ts` 不参与 prettier/eslint，保持可逐字 diff。

### R5（低）D8 修复改变了错误边界

- **是什么**：`extractAssistantText()` 对畸形 `content`（字符串 / 含 null / 缺 `text`）现在**降级为空串**，最终抛「视觉模型返回了空的转写结果」。
- **会怎么坏**：若某个调用方靠「抛 TypeError」做兜底判断，会失效。已核对 3 个调用方（`attachments.ts`、`agent-service.ts`、`settings-service.ts`）都只消费返回文本。

### R6（已关闭 2026-11-09）tests 曾「纳入类型、eslint 忽略」

- **原状**：`tsconfig.pi-server.json` 已包含 `tests/pi-server`，但 `eslint.config.js` 忽略该目录。
- **处置**：P1-1 已实测并纳入——删 ignore、`project` 指向 pi-server 程序，**50 文件 / 0 违例**。
- **仍需注意**：这些文件不在主 `tsconfig.json` 内，`projectService` 看不到它们；若有人再给该目录
  换 tsconfig，或改 `tsconfig.pi-server.json` 的 `include`，必须同步 `eslint.config.js` 里那一段，
  否则会退回「Parsing error: was not found by the project service」。

### R7（低）并发下的偶发测试超时

- **是什么**：本次首轮全量 `pnpm verify` 中 `apps/pi-web/tests/unit/mobile-runtime.test.ts` 有 1 例超时（约 6.9s），单跑与复跑均通过。
- **会怎么坏**：CI 抖动可能被误判为回归。
- **判断方法**：先单跑该文件；通过即判定为并发抖动，重跑全量确认。

### R8（已解除 2026-11-09）门禁时间随文件数增长

- **原状**：`typecheck:pi-server` 每次 `verify` 都会**再**编译 399 个文件（约 14s），加上主程序共两遍。
- **现在**：专项程序退休，`verify` 只编译一遍；pi-server 的文件数增长仍会拖慢 typecheck，但不再翻倍。
  实测主程序 17.8s（含 pi-server），专项程序 14.4s（已删除）。

### R9（已关闭 2026-11-09）G19 在 CI 落地验证

- **是什么**：门禁接入时没有 CI 运行结果。
- **验证结果**：run `42592114475`（commit `dcd483b2`）的 `Typecheck pi-server` 步骤为 success，与本地一致；
  同 job 的其余门禁步骤（typecheck / check:src / lint / format / docs）也全绿。证据细节见 §2「P0-1 验证结果」。
- **剩余风险**：CI 尚未全绿（Unit tests 的插件短路径问题，与本门禁无关），因此 build / E2E 仍未在 CI 执行；
  一旦重跑全绿，本门禁才算「在发布链路上」被真正走通。跟踪见 §2 P3-1。
