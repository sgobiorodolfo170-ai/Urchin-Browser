# 03 · 技术栈

> 状态：Draft  · 日期：2026-07-27

## 1. 核心技术选型（T1-T6）

| ID | 类别 | 选型 | 版本策略 | 决策理由摘要 |
|---|---|---|---|---|
| T1 | Electron | 最新稳定版 | `electron` 包最新 stable tag | utilityProcess API 成熟、MessagePort 完善、安全补丁跟进 |
| T2 | 前端框架 | React 18+ | 跟随主版本 | 生态/案例最多（VSCode/Discord/Slack），状态管理方案丰富 |
| T3 | 状态管理 | Zustand + 局部 XState | Zustand ^5 / XState ^5 | Zustand 主全局状态；XState 建模复杂局部状态机（下载生命周期/AI 会话状态） |
| T4 | 构建/打包 | Vite + electron-builder | Vite ^5 / electron-builder ^24 | Vite 负责 renderer HMR + 构建；electron-builder 负责 Windows 打包与签名 |
| T5 | 测试 | Vitest + Playwright | Vitest ^2 / Playwright ^1 | Vitest 三进程单元/集成；Playwright 是唯一原生支持 Electron 的 E2E |
| T6 | 原生模块 | 纯 TS + 按需 N-API/Rust | 默认 TS | 性能瓶颈再下探，避免过早引入原生复杂度 |

| 持久化 | better-sqlite3 ^11 | 主进程 SQLite 同步 API | 强制（M8 / M9 storage） |
| 敏感数据 | Electron `safeStorage` | API Key 加密 | 强制（Windows DPAPI） |
| Lint | ESLint ^9 + `@typescript-eslint` | lint 检查 | 强制（AGENTS.md §九） |
| Format | Prettier ^3 | 代码风格统一 | 强制（团队一致性） |
| Pre-commit | Husky + lint-staged | 提交时拦截不规范代码 | 强制（AGENTS.md §九 提交时卡点） |

## 3. 目录结构（v0.1 实际）

```
Urchin-Browser/
├─ apps/
│  └─ desktop/                      # 主 Electron 应用
│     ├─ src/
│     │  ├─ main/                   # 主进程
│     │  │  ├─ ai/                  # M11 AI IPC handlers / event bridge / agent factory
│     │  │  ├─ bookmarks/           # M5 Bookmark Manager
│     │  │  ├─ downloads/           # M23 Download Manager
│     │  │  ├─ extensions/          # M9-M10 Extension Loader
│     │  │  ├─ history/             # M6 History Manager
│     │  │  ├─ orchestrator/        # M11 Orchestrator（provider-registry / retry / stream / token-bucket）
│     │  │  ├─ page-context/        # M14 Page Context Extractor
│     │  │  ├─ polyfills/           # Node.js compatibility polyfills
│     │  │  ├─ protocol/            # urchin:// 协议路由
│     │  │  ├─ settings/            # M7 Settings Manager
│     │  │  ├─ storage/             # M8 SQLite + safeStorage
│     │  │  ├─ stubs/               # Node.js API stubs
│     │  │  ├─ summary/             # Summary Agent IPC handlers
│     │  │  ├─ tabs/                # M2 Tab Manager + M3 Navigation
│     │  │  └─ windows/             # M1 Window Lifecycle
│     │  ├─ renderer/               # 渲染进程
│     │  │  ├─ components/          # UI 组件（Button / Input / ProviderWarningDialog）
│     │  │  ├─ lib/                 # 工具函数（cn）
│     │  │  ├─ omnibox/             # M4 地址栏（Omnibox / PiSettingsDialog）
│     │  │  ├─ settings/            # M7 Settings 页面
│     │  │  ├─ styles/              # 全局样式
│     │  │  └─ theme/               # M19 主题系统（ThemeProvider）
│     │  └─ preload/                # preload scripts (renderer + extension)
│     ├─ electron-builder.yml
│     └─ vite.config.ts
├─ packages/
│  ├─ ipc-contract/                 # M17 zod schema + registerHandler + typedInvoke
│  ├─ ai-provider-contract/         # M12 Provider 契约 API
│  ├─ ai-extension/                 # M13 AI Side Panel React 组件
│  ├─ browser-host/                 # Host API 契约接口
│  ├─ chrome-types/                 # chrome.* API 类型定义（预加载用）
│  ├─ logger/                       # 结构化日志
│  ├─ provider-sdk/                 # Provider 子进程入口运行器
│  └─ summary-agent/                # 摘要 Agent 模块
├─ docs/                            # 设计文档体系
├─ agents.md                        # AGENTS.md（已适配）
├─ package.json                     # monorepo root (pnpm workspace)
├─ pnpm-workspace.yaml
├─ tsconfig.base.json
├─ CHANGELOG.md
└─ README.md
```

> **与设计阶段差异**：M3 Navigation 纳入 `tabs/` 而非独立目录；M11 Orchestrator 位于 `apps/desktop/src/main/orchestrator/` 而非独立的 `packages/ai-orchestrator/`（避免 utility process 包管理复杂度）；M14 Page Context 位于主进程内；M9 Chrome 兼容层仅有类型定义无运行时实现；M15 / M16 / M20-M22 未实现（见路线图）。

**Monorepo 选型**：pnpm workspace。理由：Electron 项目常需把 main/renderer/preload/utility 拆为独立构建目标，且 IPC 与 Provider 契约需作为独立 npm 包对外暴露给扩展/Provider 开发者——pnpm workspace 既能内联开发又能各自发包，比 turbo/nx 更轻。

## 4. 测试覆盖率适配门槛

> 本节是对 AGENTS.md §八默认值的**首次项目级偏离**——按 §〇.5 适配产出要求，记录原模板值、适配值与理由。**已于 2026-07-29 合并入 [../agents.md](../agents.md) §八.2 正式生效。**
> **本节是覆盖率门槛的单一真源**——[05-路线图](./05-路线图.md) 与 [06-需求文档](./06-需求文档.md) 中的覆盖率条款均引用本节，不再各自定义数值。

### 4.1 整体单元覆盖率阶梯（逐版本）

| 版本 | v0.1 | v0.2 | v0.3 | v0.4 | v0.5 | v1.0 |
|---|---|---|---|---|---|---|
| 整体单元覆盖率 | ≥60% | ≥65% | ≥70% | ≥75% | ≥75%（深度提升） | ≥80% |

原型阶段允许降至 60%（AGENTS.md §八明确允许），此后逐版本提升；v0.5 与 v0.4 持平，侧重深度而非广度。

### 4.2 分层目标

| 层级 | AGENTS.md 默认 | v0.1 适配值 | v1.0 目标 | 理由 |
|---|---|---|---|---|
| 工具类/纯函数（URL 解析/Prompt 拼装） | ≥95% | ≥90% | ≥95% | 接近纯函数，提升期短 |
| AI Provider 抽象层 | — | ≥80% | ≥90% | 第三方隔离边界，需高覆盖保证契约可靠 |
| Tab Manager (M2) | ≥90% (核心) | ≥75% | ≥90% | 核心但 v0.1 尚在迭代 |
| E2E 关键路径 | ≥100%（每路径至少一条） | 启动/导航/开关标签/AI 摘要 各至少 1 条正路 | 全覆盖 | AGENTS.md「每核心路径至少一条正向用例」按 v0.1 范围适配；v0.2 起增加隐私拦截/扩展加载路径 |

**过渡计划**：按 §4.1 阶梯逐版本提升，每次提升需在 CHANGELOG 记录覆盖率提升议题作为验收信号。

| 阶段 | 卡点 | 工具 |

## 7. 测试约定

### 7.1 测试文件命名

| 测试类型 | 文件命名 | 示例 |
|---|---|---|
| 单元测试 | `*.test.ts` | `tab-manager.test.ts` |
| 集成测试 | `*.integration.test.ts` | `ipc-protocol.integration.test.ts` |
| E2E 测试 | `*.e2e.ts` | `navigation.e2e.ts` |

### 7.2 测试结构（describe/it 风格）

```typescript
describe('TabManager', () => {
  describe('create', () => {
    it('should create a new tab and return its snapshot', async () => {
      // ...
    });
    it('should bind webContents lifecycle events on creation', async () => {
      // ...
    });
    it('should associate tab with the correct window', async () => {
      // ...
    });
  });

  describe('remove', () => {
    it('should destroy webContents and remove from map', async () => {
      // ...
    });
    it('should emit "removed" event', async () => {
      // ...
    });
  });
});
```

### 7.3 Mock 策略

| 层级 | Mock 策略 | 工具 |
|---|---|---|
| 单元测试 | 函数级 mock，不跨界 | `vitest.mock()` |
| 集成测试 | 轻量 mock Electron API（如 `BrowserWindow` / `ipcMain`） | `vitest-mock-extended` |
| E2E 测试 | 真实 Electron 实例，不 mock 任何东西 | Playwright `_electron.launch` |

### 7.4 测试数据管理

- 测试数据（mock URLs、Provider 配置、历史记录等）统一放在 `__fixtures__/` 目录中，与测试文件同层级。
- 用于测试的 Provider 插件（模拟 Provider）放在 `fixtures/test-provider/` 目录下，作为独立 npm 包引用。
- 数据库测试使用 `:memory:` SQLite 模式，不在测试间共享状态。

### 7.5 覆盖率门槛

详见 §4 测试覆盖率适配门槛。v0.1 整体 ≥60%，提交时覆盖率检查失败则拒绝提交。
