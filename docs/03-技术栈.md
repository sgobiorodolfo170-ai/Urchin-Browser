## 1. 核心技术选型（T1-T6）

| ID | 类别 | 选型 | 版本策略 | 决策理由摘要 |
|---|---|---|---|---|
| T1 | Electron | 最新稳定版 | `electron` 包最新 stable tag | utilityProcess API 成熟、MessagePort 完善、安全补丁跟进 |
| T2 | 前端框架 | React 18+ | 跟随主版本 | 生态/案例最多（VSCode/Discord/Slack），状态管理方案丰富 |
| T3 | 状态管理 | Zustand | Zustand ^5 | Zustand 主全局状态；复杂局部状态机（下载生命周期等）用手写状态机实现——XState 最终未引入（v0.1.0-dev.23 清理死依赖） |
| T4 | 构建/打包 | Vite + electron-builder | Vite ^5 / electron-builder ^26.15.3 | Vite 负责 renderer HMR + 构建；electron-builder 负责 Windows 打包与签名 |
| T5 | 测试 | Vitest + Playwright | Vitest ^2 / Playwright ^1 | Vitest 三进程单元/集成；Playwright 是唯一原生支持 Electron 的 E2E |
| T6 | 原生模块 | 纯 TS + 按需 N-API/Rust | 默认 TS | 性能瓶颈再下探，避免过早引入原生复杂度 |

> 连带版本更新：T1 Electron 32.3.3 → **43.7.3**（对齐上游 `^43.3.0`）；T4 electron-builder ^24 → **^26.15.3**；

> （Urchin 自研 Tiptap 2 编辑器保留为保底回落，融合路径稳定后退役）。

**Monorepo 选型**：pnpm workspace。理由：Electron 项目常需把 main/renderer/preload/utility 拆为独立构建目标，且 IPC 与 Provider 契约需作为独立 npm 包对外暴露给扩展/Provider 开发者——pnpm workspace 既能内联开发又能各自发包，比 turbo/nx 更轻。

## 4. 测试覆盖率适配门槛

> 本节是对 AGENTS.md §八默认值的**首次项目级偏离**——按 §〇.5 适配产出要求，记录原模板值、适配值与理由。
> **本节是覆盖率门槛的唯一真源**（2026-10-27 单向化）——[../agents.md](../agents.md) §八.2 只作摘录，[05-路线图](./05-路线图.md) 与 [06-需求文档](./06-需求文档.md) 中的覆盖率条款均引用本节，不再各自定义数值。**任何阶梯数值调整只改本节 + `apps/desktop/vitest.config.ts` 的 `thresholds`，其余位置一律回改摘录。**

### 4.1 整体单元覆盖率阶梯（逐版本）

| 版本 | v0.1 | v0.2 | v0.3 | v0.4 | v0.5 | v1.0 |
|---|---|---|---|---|---|---|
| 整体单元覆盖率 | ≥60% | ≥65% | ≥70% | ≥75% | ≥75%（深度提升） | ≥80% |

原型阶段允许降至 60%（AGENTS.md §八明确允许），此后逐版本提升；v0.5 与 v0.4 持平，侧重深度而非广度。

**实测记录**（本表为达成证据台账，每个 stable 版本收口时补一行）：

| 版本 | 门槛 | 实测 lines / branch / functions            | 记录位置               |
| ---- | ---- | ------------------------------------------ | ---------------------- |
| v0.2 | ≥65% | 69.18% / 79.57% / 77.12%（`apps/desktop`） | CHANGELOG v0.2.0 条目  |

**执行机制**：`apps/desktop/vitest.config.ts` 的 `coverage.thresholds` 四维均设 65，`pnpm verify`（= typecheck + lint + `test:coverage` + `check:docs`）与 CI 低于门槛即失败。门槛值与 `thresholds` 必须成对修改。

> ⚠ **采集完整性前提（2026-10-27 发现）**：`apps/desktop` 共 120 个测试文件。若某次运行只收集到 117~119 个（宿主文件系统限制导致个别文件加载失败，伴随 Unhandled Error），整体覆盖率会从 69.18% 掉到 56~66%，并可能误触发分层门槛。**判断方法：看 `Test Files` 是否为 120**——不是 120 属采集不全，不是代码退化。覆盖率结论以 CI 全量运行为准。

### 4.2 分层目标

| 层级 | AGENTS.md 默认 | v0.1 适配值 | v1.0 目标 | 理由 |
|---|---|---|---|---|
| 工具类/纯函数（URL 解析/Prompt 拼装） | ≥95% | ≥90% | ≥95% | 接近纯函数，提升期短 |
| AI Provider 抽象层 | — | ≥80% | ≥90% | 第三方隔离边界，需高覆盖保证契约可靠 |
| Tab Manager (M2) | ≥90% (核心) | ≥75% | ≥90% | 核心但 v0.1 尚在迭代 |
| E2E 关键路径 | ≥100%（每路径至少一条） | 启动/导航/开关标签 各至少 1 条正路（`launch.spec.ts` / `tab-order-repro.spec.ts`）；AI 摘要暂不覆盖 | 全覆盖 | 依据 AGENTS.md §八.2；AI 摘要依赖真实 Provider + API key，见 `launch.spec.ts` 文件头注释；v0.2 起增加隐私拦截/扩展加载路径 |

**过渡计划**：按 §4.1 阶梯逐版本提升，每次提升需在 CHANGELOG 记录覆盖率提升议题作为验收信号。

## 5. CI/CD 门槛（v0.1）

| 阶段 | 卡点 | 工具 |
|---|---|---|
| 写代码时 | IDE 实时提示 | ESLint + Prettier VSCode 插件 |
| 提交时 | Git Hook pre-commit | Husky + lint-staged：ESLint --fix + Prettier --write（仅暂存文件）；typecheck 与单测由下方 CI 兜底（依据 [../agents.md](../agents.md) §九.2） |
| PR | CI 流水线 | GitHub Actions：`pnpm typecheck` + `pnpm lint` + `pnpm test:coverage` + `pnpm e2e` |
| 发布 | 人工确认门禁 | 人工跑 `pnpm e2e` 全套、检查覆盖率报告、签名验证、再发布 |

**发布通道矩阵（ADR-012）**：

| 通道 | 版本 | GitHub 标记 | 更新清单 | 检查顺序 |
|---|---|---|---|---|
| dev | `X.Y.0-dev.NNN` | Pre-release | `dev.yml` | 先 dev，无更新再 latest |
| stable | `X.Y.0` | Latest | `latest.yml` | 只查 latest |

`scripts/build-version.mjs` 从 CHANGELOG 表尾派生 channel/releaseType 并做 stable 基线门禁；`scripts/package-win.mjs` 打包后校验 exe + blockmap + 对应 yml，且拒绝另一通道的 yml。详见 [ADR-012](./decisions/ADR-012-发布通道与版本号治理.md)。

## 7. 测试约定

### 7.1 测试文件命名

| 测试类型 | 文件命名 | 示例 |
|---|---|---|
| 单元测试 | `*.test.ts` | `tab-manager.test.ts` |
| 集成测试 | `*.integration.test.ts` | `ipc-protocol.integration.test.ts`（当前未启用，均以单元测试承载） |
| E2E 测试 | `*.spec.ts` | `launch.spec.ts`（Playwright 约定后缀；设计期曾写作 `*.e2e.ts`，以现状为准） |

### 7.2 测试结构（describe/it 风格）

```typescript

  describe('create', () => {
    it('should create a new tab and return its snapshot', async () => {
      // ...
    });
    it('should bind webContents lifecycle events on creation', async () => {
      // ...
    });
    it('should associate tab with the correct window', async () => {
      // ...
    });
  });

  describe('remove', () => {
    it('should destroy webContents and remove from map', async () => {
      // ...
    });
    it('should emit "removed" event', async () => {
      // ...
    });
  });

```

### 7.3 Mock 策略

| 层级 | Mock 策略 | 工具 |
|---|---|---|
| 单元测试 | 函数级 mock，不跨界 | `vitest.mock()` |
| 集成测试 | 轻量 mock Electron API（如 `BrowserWindow` / `ipcMain`） | `vitest-mock-extended` |
| E2E 测试 | 真实 Electron 实例，不 mock 任何东西 | Playwright `_electron.launch` |

### 7.4 测试数据管理

- 测试数据（mock URLs、Provider 配置、历史记录等）统一放在 `__fixtures__/` 目录中，与测试文件同层级。
- 用于测试的 Provider 插件（模拟 Provider）放在 `fixtures/test-provider/` 目录下，作为独立 npm 包引用。
- 数据库测试使用 `:memory:` SQLite 模式，不在测试间共享状态。

### 7.5 覆盖率门槛

详见 §4 测试覆盖率适配门槛。v0.1 整体 ≥60%，提交时覆盖率检查失败则拒绝提交。
