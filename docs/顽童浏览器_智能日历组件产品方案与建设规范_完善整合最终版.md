## 1. 执行摘要

### 1.1 建设结论

Urchin Browser 的日历应建设为**本地优先、AI 可调用、用户可视化管理的基础能力组件**，而不是拥有独立对话入口、独立 Agent、独立模型调用链和独立智能策略的第二套 AI 产品。

日历组件负责：

1. 管理日历、日程、重复规则、提醒配置和跨模块关联引用。
2. 提供事件增删改查、时间范围查询、冲突检测和空闲时间查询等确定性能力。
3. 正确处理全天、跨天、时区、夏令时和重复事件边界。
4. 提供符合 Urchin 工程规范的 Main 服务、SQLite 存储和 typed IPC。
5. 提供稳定的 AI Tool 定义、参数 Schema、结构化响应和错误码。
6. 提供主 AI 可组合使用的提示词片段、上下文规范、工具使用手册和安全规则。
7. 提供轻量可视化日历窗口，满足用户查看和手动维护日程的需要。

主 AI 助理负责：

1. 理解自然语言、识别意图并澄清歧义。
2. 根据上下文决定调用哪些日历工具。
3. 结合任务、项目、联系人、邮件、剪藏和知识库进行跨模块推理。
4. 制定计划、比较候选时间、提出建议并决定是否需要用户确认。
5. 生成每日简报、每周计划、时间复盘和主动服务内容。
6. 负责复杂自动化和多 Agent 协调，不把这些能力重复建设在日历组件内部。

**核心原则：主 AI 负责理解、规划与决策；日历负责保存事实、执行确定性操作、校验规则并返回可信结果。**

### 1.2 首期建设目标

首期（P0）不追求完整商业日历产品的全部体验，优先完成以下闭环：

- 在速记页左区现有“+”按钮左侧增加日历图标入口。
- 点击后打开速记页内日历模态窗口，关闭后完整恢复原速记页状态。
- 提供月视图、日程列表、事件详情和基础事件 CRUD。
- 建立本地默认日历和可扩展的多日历领域模型。
- 建立完整的时间语义、重复事件和跨模块关系数据契约；复杂重复规则的执行可在 P1 完成。
- 在 Main 进程提供 CalendarService，通过 M17 typed IPC 对 Renderer 暴露受控接口。
- 设计完整的 AI Tool 契约，包括日历列表、事件 CRUD、冲突检测和空闲时间查询；首期至少完成核心工具与 Mock Tool Host 验证。
- 提供完整的提示词片段、上下文结构、工具选择规范和 AI 日历使用手册。
- 建立权限校验、错误码、幂等、版本控制、审计及基础数据保护机制。

真实主 AI 工具路由的联调取决于主 AI 助理模块的实际建设进度。日历模块不得因此建立第二条独立模型调用链。

### 1.3 成功标准

- 用户可以从指定入口打开日历，且不破坏 M27 速记页原有结构和状态。
- 本地日程增删改查可靠，应用重启后数据仍然存在。
- 日历的 UI、IPC、AI Tool 使用同一套领域规则和数据语义。
- AI 能查询日历、定位事件、创建与修改事件，并正确处理冲突、重复规则和权限错误。
- AI 不会因缺少上下文而编造日期、时长、参与者、提醒或日历目标。
- 多日历、重复事件、事件关联等扩展不需要推翻首期数据模型和工具契约。
- `pnpm verify`、受影响的测试、构建和实际界面验收通过。

## 2. 项目背景与架构适配

### 2.1 项目形态

Urchin Browser 是基于 Electron 与 Chromium 内核构建的桌面浏览器，采用 pnpm monorepo、React、TypeScript、Vite、Zustand、SQLite、Zod、Radix UI、Tailwind CSS、Vitest 与 Playwright 等项目技术体系，并采用 Main、Renderer、Preload 及 AI Utility / Provider Child 等进程分层。

日历必须遵循项目既有工程边界：

- 不引入独立后端服务来实现本地日历核心能力。
- 不绕开项目 IPC 契约，不允许 Renderer 直接访问 SQLite。
- 不将日历业务数据混入 AI 对话数据库。
- 不让 Provider Child 获得主业务数据库连接。
- 不硬绑定某个模型、Provider 或具体 AI Harness。

实际实现前必须核对当前源码和依赖版本。本文中的目录、模块编号、Schema 和通道名称为设计建议，不代表源码中已经存在。

### 2.2 与 M27 速记页的关系

日历入口位于 `urchin://notebook` 速记页左区顶部工具区域，紧邻现有“+”按钮，并且在“+”左侧。

```text
┌──────────────────────────────────────┐
│ 速记页                               │
├──────────────────────────────────────┤
│ 左区顶部工具区域                     │
│                                      │
│              [日历图标] [+]         │
│                                      │
│ 笔记本 / 页面树                      │
│  ├─ 页面 A                           │
│  ├─ 页面 B                           │
│  └─ 页面 C                           │
└──────────────────────────────────────┘
```

约束：

1. 日历按钮与“+”按钮是并列、独立的操作。
2. “+”按钮原有创建笔记本或页面的行为必须完全保持不变。
3. 不改变 M27 左、中、右三区布局、默认比例、分割线、笔记树和画布状态。
4. 日历事件与速记页笔记、任务清单、便利贴保持数据边界，通过稳定 ID 进行可选关联。
5. 日历窗口关闭后回到原页面，不重载 `urchin://notebook`。

### 2.3 与 M8 存储体系的关系

根据项目存储契约，日历属于浏览器业务数据，默认写入主 SQLite 数据库 `urchin.db`，通过 M8 migration 管理 schema。

- 日历、日程、重复规则、提醒和关联引用写入 `urchin.db`。
- 不写入 `ai.db`，避免业务日程与 AI 对话 / Provider 数据混合。
- 不将全部事件塞入 `notebook.state` 或其他 Settings JSON 大对象。
- 仅将界面偏好等轻量配置写入独立 Settings 键，例如 `calendar.ui-state`。
- 数据库变更必须追加 migration，不得手工改写用户已有数据库文件。
- 具体表名、ID 格式、时间戳单位和 migration 编号以当前 M8 实现为准。

### 2.4 与 M17 IPC 与安全体系的关系

项目已有 typed IPC 和 Zod 双向校验约定。日历应在项目 IPC Schema 单一真源中新增 `calendar.*` 契约，并遵循 `<domain>.<action>` 点分命名规则。

基本调用链：

```text
Calendar Renderer
      │
      ▼
Preload 暴露的受控 API
      │
      ▼
M17 typedInvoker / IPC Schema
      │
      ▼
Main calendar handlers
      │
      ▼
CalendarService
      │
      ▼
CalendarRepository
      │
      ▼
urchin.db
```

Handler 只负责 Schema 校验、上下文和权限检查、调用 Service、映射结果；SQL 不得散落在 IPC Handler 中。

### 2.5 与 AI 基础设施的关系

项目已有 AI Orchestrator、Provider Plugin API、AI Side Panel 等基础设施。Provider 是否支持 function calling 属于 Provider capability，日历不能默认所有模型均支持原生工具调用。

- 日历不自行发起 LLM 请求，不维护独立对话，不拥有独立 Agent。
- 日历提供模型无关的 Tool 名称、Schema、描述、约束和结果语义。
- 未来主 AI 助理通过统一 Tool Registry / Tool Gateway 注册并执行日历工具。
- 工具执行最终进入受信任的 Main CalendarService，不允许模型直连数据库。
- Provider 不支持原生 function calling 时，由主 AI 工具路由层处理，不改变日历领域接口。
- pi-web / 编码 Agent / Harness 不应默认被视为面向普通用户的日历助理入口。

### 2.6 现状依据与核对要求

本方案按项目公开文档中关于 M27 速记页、M8 存储、M17 IPC、M12 Provider capability、AI Orchestrator 和工程质量门禁的描述进行适配。公开文档记录与实际工作区可能存在时间差。

开发前须核对：

1. M27 左区顶部工具栏实际组件与“+”按钮实现。
2. M8 主库初始化、migration 注册和 Repository 模式。
3. M17 IPC Schema 单一真源、typedInvoker、handler 注册与 preload 暴露方式。
4. M19 ThemeProvider、图标库和 Radix Dialog 现有封装。
5. 通知 / Toast 能力是否已有 Main 端持久调度服务。
6. AI Tool Registry / Tool Gateway 是否已经实现，以及当前工具执行上下文如何注入用户身份。
7. 项目 `AGENTS.md`、`pnpm verify`、E2E 选择性执行和文档索引的最新约束。

不得将本文的建议目录或通道误认为现有代码实现。

## 3. 产品定位、价值与设计原则

### 3.1 产品定位

**M28 Calendar 是 Urchin Browser 的本地时间与日程基础能力组件。**它通过速记页入口提供轻量日历窗口，并向主 AI 助理提供可靠、标准化、权限受控的时间数据和操作接口。

它不是独立 AI 日历产品，不负责全局个人规划，也不取代任务、项目、联系人、邮件、知识库或统一通知中心。

### 3.2 产品价值

| 价值方向 | 用户结果 | 组件提供的支撑 |
|---|---|---|
| 时间可见 | 快速查看某天、某周和未来安排 | 月、周、日、议程视图及事件查询 |
| 统一记录 | 工作、生活、学习安排集中管理 | 多日历、事件管理和分类 |
| 低成本操作 | 通过主 AI 以自然语言管理日程 | Tool Schema、上下文、提示词和手册 |
| 时间协调 | 找到不冲突的候选时间 | 冲突检测和空闲时段查询 |
| 变化可控 | 修改前知道影响，修改后可追溯 | 版本控制、审计、撤销和恢复 |
| 业务联动 | 日程与任务、项目、联系人及资料关联 | 关系 ID 和跨模块协作约定 |

### 3.3 设计原则

1. **单一职责**：日历拥有日历领域的数据和规则，不复制其他模块的业务状态。
2. **接口优先**：核心能力应可由主 AI 稳定调用；UI 负责查看和必要的人工纠错。
3. **先可靠，再智能**：时间、时区、重复、数据一致性优先于花哨交互。
4. **确定性计算与 AI 判断分离**：重叠检测、空闲计算由服务端执行；排期取舍和解释由主 AI 完成。
5. **模型无关**：Tool Schema 不依赖特定 Provider 的调用格式。
6. **写入可控**：关键写操作有权限、确认、幂等、版本控制和审计。
7. **结果可验证**：写入成功与否以 CalendarService 返回结果为准。
8. **上下文最小化**：只向模型传递当前任务需要的日历数据。
9. **渐进集成**：先完成本地日历，再按需求引入外部同步和邀请。
10. **契约先行、实现分期**：P0 可以预留 P1/P2 所需字段和接口，不等于提前实现所有复杂功能。

## 4. 职责边界与建设范围

### 4.1 日历组件负责

| 职责 | 说明 |
|---|---|
| 日历数据管理 | 日历列表、默认日历、名称、颜色、时区、启用状态 |
| 事件管理 | 事件创建、查询、修改、删除、取消与状态维护 |
| 时间规则 | 全天、跨天、时区、夏令时、半开区间和重复事件 |
| 查询服务 | 时间范围、日历、关键字、状态、分页查询 |
| 冲突检测 | 按事件时间区间执行确定性重叠判断 |
| 空闲时段查询 | 根据时间范围、时长、工作时间和缓冲规则计算候选时段 |
| 提醒配置 | 保存提醒规则，联动本地调度或通知中心 |
| 关联引用 | 以类型和对象 ID 关联任务、项目、联系人、文件或邮件 |
| AI 契约 | Tool 名称、参数 Schema、结构化响应和错误码 |
| AI 使用资料 | 系统提示词片段、上下文结构、操作手册和安全规则 |
| 可视化界面 | 月、周、日、议程等日历展示及人工维护 |
| 数据安全 | 权限检查、幂等、版本、审计、软删除和恢复策略 |

### 4.2 主 AI 助理负责

- 自然语言理解、日期时间解析和歧义澄清。
- 根据当前时间、时区和用户偏好解释相对日期。
- 调度日历、任务、项目、联系人、邮件和知识库工具。
- 根据目标、优先级、预计耗时和空闲时段生成计划。
- 对多个候选时间排序、解释选择理由并与用户沟通。
- 每日简报、每周计划、时间复盘、时间预算和习惯分析。
- 主动提醒的策略、跟进时机和自然语言表达。
- 会议资料准备、会议纪要和行动项整理（依赖对应模块能力）。
- 跨模块自动化和多 Agent 协调。

### 4.3 不由日历组件重复建设

- 独立 AI Agent、独立大模型调用链和独立聊天界面。
- 自然语言理解、思维链、长期目标理解和自主决策逻辑。
- 每日简报、每周复盘、时间画像、精力分析和时间预算。
- 待办状态机、项目管理、目标管理和复杂甘特图。
- 邮件理解、文件解析、知识检索和联系人关系维护。
- 会议录音、语音转写、会议纪要和行动项分配。
- 通用自动化规则引擎、多智能体协调器和时间数字孪生。
- 天气、交通、位置和现实世界信息的综合判断。

这些能力由主 AI 或对应业务模块统一实现，日历只提供数据和工具能力。

### 4.4 功能实现与契约预留的区别

| 能力 | P0 设计 / 契约要求 | 实现阶段 |
|---|---|---|
| 多日历 | 完整 Calendar 数据模型、列表接口、默认日历语义 | P0 单默认日历；P1 多日历管理 UI |
| 重复事件 | recurrence 字段、系列 ID、例外模型、Tool 参数预留 | P1 完整规则与例外执行 |
| 事件关联 | EventRelation 模型和 Tool `relations` 参数 | P1 连接已具备稳定 ID 的业务模块 |
| 参与者 | 数据字段 / 引用模型预留，不自动发邀请 | P1 基础参与者引用；P2 邀请和回复 |
| 会议链接 | `meetingUrl` 字段预留和安全展示规则 | P0 可保存普通链接；外部会议协作按需增强 |
| 空闲时段 | Tool 和 IPC 契约定义、边界规则 | P1 完整查询和排期联调 |
| 提醒 | reminder 数据模型、配置接口和调度边界 | P1 本地调度与通知联动 |
| 外部同步 | 领域边界和集成接口扩展点 | P2/P3 |
| 周 / 日视图 | 交互与组件扩展约定 | P1 |
| 年视图 | 需求与视图扩展约定 | P2 |

## 5. 用户场景与功能需求

### 5.1 查询日程

用户：“我明天有什么安排？”

主 AI 从系统上下文读取当前时间和时区，计算明天的本地日期范围，调用 `calendar_list_events`，按时间顺序展示事件。日历只返回当前用户有权访问的数据。

### 5.2 创建日程

用户：“明天下午三点和小李讨论需求，预留半小时，提前十分钟提醒我。”

主 AI 负责解析日期、时间、标题、时长、参与人和提醒要求；必要时调用联系人工具消除姓名歧义；调用日历列表确定目标日历；检查冲突后创建。日历服务负责合法性校验并返回规范化事件。

### 5.3 修改日程

用户：“把明天的产品评审推迟半小时。”

主 AI 先查询并唯一定位事件，再读取最新版本，按原持续时长平移开始和结束时间，执行冲突检测，最后调用更新工具。若为重复事件，必须明确修改范围。

### 5.4 删除或取消日程

“删除本周五的例会”可能指单次实例，也可能指整个系列。AI 必须先查询目标并确定作用范围。删除本地记录与向参与者发送取消通知是两项不同操作。

### 5.5 查找空闲时间

用户：“下周找一个一小时的空档，尽量安排在下午。”

主 AI 将时间范围、持续时长和偏好转换为结构化参数，调用 `calendar_find_free_slots`。日历只根据已接入并有权访问的日历及明确提供的工作时间、缓冲规则计算候选空档。空档不代表现实世界绝对可用。

### 5.6 任务与日程联动

用户：“把完成产品方案安排到这周日历里。”

主 AI 先调用任务模块获取任务标题、优先级、预计耗时和截止日期，再调用空闲时间查询工具，提出候选时间。按用户确认策略创建日程，并写入 `task` 类型关联引用。任务状态仍由任务模块维护。

### 5.7 会议与资料关联

用户：“帮我找到明天的项目评审，并关联最新需求文档。”

主 AI 查询日程，再调用文件或知识库模块检索资料，最后向日程关联记录写入文件 ID。日历不负责解析文档正文。

### 5.8 周期性安排

用户：“以后每周一上午九点安排半小时项目同步。”

主 AI 解析重复规则、开始日期、结束条件和日历目标，通过 `recurrence` 参数创建系列事件。P1 实现重复规则和例外的完整服务端执行；P0 先固定数据语义和工具契约。

### 5.9 多日历管理

用户可以建立工作、生活、学习、家庭等日历，并设置颜色、默认日历和可见性。首期即使 UI 只有默认日历，也要通过 `calendar_list_calendars` 为 AI 和后续 UI 提供稳定入口。

### 5.10 事件回顾与历史查询

用户：“上个月我参加了多少次项目会议？”

主 AI 查询所需时间范围内的日历数据，再结合项目关联或事件分类进行汇总。日历组件只提供准确记录，不负责生成长期时间画像。

- 焦点管理符合 Dialog 可访问性要求，关闭后焦点回到入口。

## 8. 时间、重复事件、冲突与空闲规则

### 8.1 日期与时间标准

- 对外时间使用 ISO 8601。
- 定时事件必须携带明确时区偏移，并保存 IANA 时区。
- 内部可使用 UTC 时间戳作为时间瞬间的比较依据，同时保留原始 / 关联 IANA 时区。
- 全天事件使用本地日期值，不转换为 UTC 午夜。
- 用户未指定时区时，使用应用设置；若暂未提供应用级设置，使用操作系统本地时区，并明确注入 AI 上下文。
- 不允许 Renderer、Main 和 AI 各自采用不同转换规则。

### 8.2 半开区间

定时事件采用 `[start, end)`：

- A：10:00–11:00；B：11:00–12:00，首尾相接不冲突。
- A：10:00–11:00；B：10:30–11:30，视为冲突。
- 结束时间必须严格晚于开始时间。

全天事件使用 `[startDate, endDateExclusive)`。例如 2026-11-16 全天表示开始日期 `2026-11-16`、结束日期 `2026-11-17`。

### 8.3 重复事件

P1 至少支持：

- 每天、每周、每月、每年。
- 间隔规则，例如每 2 周。
- 指定星期几或日期规则。
- 按结束日期或重复次数终止。
- 单次实例覆盖（时间、标题或状态）。
- 单次实例取消。
- 修改范围：仅本次、本次及以后、整个系列。

重复规则必须按系列所属 IANA 时区的本地墙钟时间展开，不能简单给首个实例加固定毫秒数。系列规则修改可能需要拆分系列，应由 Service 负责事务和一致性处理。

### 8.4 冲突检测

定时事件冲突条件：

```text
existing.start < proposed.end
AND existing.end > proposed.start
```

检测时：

- 支持 `excludeEventId`，避免修改事件与自身冲突。
- 只比较指定且有权访问的日历。
- 排除已取消事件。
- 正确处理全天事件占用的本地日期。
- 对重复事件只展开查询范围内可能出现的实例。
- 返回事件 ID、标题、时间和冲突区间，不自动替用户改期。

冲突检测只判断明确的时间重叠，不替代 AI 对地点距离、通勤时间、用户精力或业务优先级的判断。

### 8.5 空闲时间查询

输入至少包括：

- 搜索开始和结束时间。
- 目标连续时长（分钟）。
- 参与计算的日历 ID 集合。
- 用户工作日和工作时间（可选）。
- 午休 / 不可用时间（可选）。
- 前后缓冲分钟数（可选）。
- 排除的事件 ID（可选）。
- 最大候选数量。

仅返回满足输入约束的候选区间，不等于用户已经预约或现实中一定空闲。没有工作时间配置时，不得伪造用户偏好。

### 8.6 夏令时与时区切换

- 重复事件按所属时区的本地墙钟时间展开。
- 夏令时跳过或重叠时段按统一日期时间库策略处理。
- 无法唯一解析的本地时间返回 `TIMEZONE_AMBIGUOUS`，不静默挪动时间。
- 用户旅行或系统时区变化时，不应无提示地改写已保存事件的绝对时间。
- 全天事件保持其原始日期语义。

## 9. 主进程服务与 IPC 接口规范

### 9.1 模块内部结构

建议新增 Calendar 域模块，按项目当前 Main 模块组织方式调整：

- `calendar-service`：业务规则入口。
- `calendar-repository`：SQLite 读写。
- `calendar-time`：日期、时区、区间和转换。
- `calendar-recurrence`：重复系列展开及例外（P1）。
- `calendar-reminder-scheduler`：本地提醒调度（P1）。
- `calendar-handlers`：IPC handlers。
- `calendar-schema`：领域和 IPC Schema（放置位置遵循项目 IPC 契约单一真源）。

### 9.2 IPC 通道建议

| IPC 通道 | 请求核心字段 | 说明 |
|---|---|---|
| `calendar.list` | `includeDisabled?` | 查询日历列表，P0 |
| `calendar.create` | `name`、`color?`、`timeZone` | 新建日历，P1 UI；P0 契约预留 |
| `calendar.update` | `id`、`patch`、`expectedVersion` | 更新日历，P1 |
| `calendar.archive` | `id`、`expectedVersion` | 归档日历，P1 |
| `calendar.events.query` | `from`、`to`、`calendarIds?`、筛选和分页 | 事件范围查询，P0 |
| `calendar.event.get` | `id` | 读取单事件，P0 |
| `calendar.event.create` | 事件字段、`requestId` | 创建事件，P0 |
| `calendar.event.update` | `id`、`patch`、`expectedVersion`、`scope?` | 修改事件，P0 基础 / P1 系列 |
| `calendar.event.delete` | `id`、`scope`、`requestId` | 删除事件，P0 基础 / P1 系列 |
| `calendar.conflicts.check` | `start`、`end`、`calendarIds`、`excludeEventId?` | 冲突检测，P0 |
| `calendar.freebusy.query` | 日期范围、时长、工作时间、缓冲等 | 空闲查询，P1 |
| `calendar.reminders.update` | `eventId`、提醒数组 | 提醒配置，P0 契约 / P1 调度 |
| `calendar.events.changed` | 事件 ID、变更类型、版本 | 需要跨视图通知时使用，按需 |

通道名是建议契约，最终必须与项目已有命名规则和 Schema 真源一致。若当前项目使用其他命名风格，应保持语义一致并按规范映射。

### 9.3 Schema 示例

以下仅示范字段约束；实际 Zod 导入、ID 类型、错误包装和文件位置按项目既有写法落实。

```ts
import { z } from 'zod'

const IdSchema = z.string().min(1).max(128)
const DateSchema = z.string().regex(/^\\d{4}-\\d{2}-\\d{2}$/)
const IsoDateTimeSchema = z.string().datetime({ offset: true })
const TimeZoneSchema = z.string().min(1).max(64)

const ReminderSchema = z.object({
  method: z.enum(['in_app', 'system']),
  minutesBefore: z.number().int().min(0).max(525_600),
})

const RelationSchema = z.object({
  type: z.enum(['task', 'project', 'contact', 'note', 'file', 'email']),
  id: IdSchema,
})

const RecurrenceSchema = z.object({
  frequency: z.enum(['daily', 'weekly', 'monthly', 'yearly']),
  interval: z.number().int().min(1).max(99).default(1),
  byWeekday: z.array(z.number().int().min(0).max(6)).optional(),
  startDate: DateSchema,
  endDate: DateSchema.optional(),
  count: z.number().int().positive().optional(),
  timeZone: TimeZoneSchema,
}).strict()

export const CalendarEventCreateSchema = z.object({
  calendarId: IdSchema,
  title: z.string().trim().min(1).max(200),
  description: z.string().max(20_000).nullable().optional(),
  location: z.string().max(500).nullable().optional(),
  meetingUrl: z.string().url().nullable().optional(),
  allDay: z.boolean(),
  startAt: IsoDateTimeSchema.optional(),
  endAt: IsoDateTimeSchema.optional(),
  startDate: DateSchema.optional(),
  endDateExclusive: DateSchema.optional(),
  timeZone: TimeZoneSchema,
  status: z.enum(['confirmed', 'tentative']).default('confirmed'),
  visibility: z.enum(['private', 'default']).default('private'),
  recurrence: RecurrenceSchema.nullable().optional(),
  reminders: z.array(ReminderSchema).max(8).default([]),
  relations: z.array(RelationSchema).max(50).default([]),
  requestId: IdSchema,
}).strict().superRefine((value, ctx) => {
  if (value.allDay) {
    if (!value.startDate || !value.endDateExclusive || value.startAt || value.endAt) {
      ctx.addIssue({ code: 'custom', message: '全天事件必须使用日期区间，不能提交定时字段' })
    }
  } else if (!value.startAt || !value.endAt || value.startDate || value.endDateExclusive) {
    ctx.addIssue({ code: 'custom', message: '定时事件必须使用开始和结束时间，不能提交全天日期字段' })
  }
})
```

### 9.4 Handler 规则

- 所有 handler 通过项目统一注册函数注册。
- 请求和响应均进行 Schema 校验。
- Handler 只处理上下文、权限、Service 调用和错误映射。
- SQL 仅出现在 Repository。
- Renderer 不得传入 SQL、表名、任意文件路径或任意回调。
- 写操作检查身份、目标权限、幂等请求 ID 和版本号。
- 不向 Renderer 或模型暴露数据库堆栈、绝对本地路径和敏感内部数据。

### 9.5 并发、幂等与更新

- 创建接口使用 `requestId` / 幂等键；同一请求重试返回原结果，不重复创建。
- 更新接口要求 `expectedVersion`；版本不匹配返回 `VERSION_CONFLICT`。
- 删除接口对重复系列必须要求修改范围。
- 写操作应具备事务边界；事件修改后提醒和关联状态需要可靠同步。
- UI 使用 Service 返回的权威事件对象更新展示。

### 9.6 事件推送

首期 CRUD 使用请求-响应 RPC 即可，不为普通日历刷新强制引入流式 MessagePort。若需要多窗口或多个视图同步，可推送经过 Schema 校验的 `calendar.events.changed`，负载包含事件 ID、变更类型和版本号；Renderer 收到后重新查询权威数据。

## 10. AI Tool 接口规范

### 10.1 设计原则

IPC 与 AI Tool 是两层不同契约：

- IPC 面向 Urchin 内部 Renderer / Main 通信。
- AI Tool 面向主 AI 助理的工具注册和调用。
- AI Tool 由受信任的 Tool Gateway 执行，再调用 CalendarService。
- 模型只能提供结构化参数，不能访问 SQLite、Node.js、文件系统或 Electron API。
- Tool Schema 应独立于 Provider，Provider function calling 只是调用适配方式。
- Tool 的定义、参数、提示词和手册必须保持版本一致。

### 10.2 工具清单

| Tool | 用途 | 类型 | 阶段 |
|---|---|---|---|
| `calendar_list_calendars` | 查询用户可访问日历及权限 | 只读 | P0 |
| `calendar_list_events` | 按时间范围查询事件 | 只读 | P0 |
| `calendar_get_event` | 获取单个事件详情 | 只读 | P0 |
| `calendar_create_event` | 创建单次或重复事件 | 写入 | P0 基础 / P1 重复 |
| `calendar_update_event` | 修改事件或系列 | 写入 | P0 基础 / P1 系列 |
| `calendar_delete_event` | 删除或取消事件 | 写入 | P0 基础 / P1 系列 |
| `calendar_check_conflicts` | 检查拟定时间冲突 | 只读计算 | P0 |
| `calendar_find_free_slots` | 查询候选空闲时段 | 只读计算 | P1；P0 定义契约 |

### 10.3 `calendar_list_calendars`

参数：

```json
{ "includeArchived": false }
```

返回日历 ID、名称、颜色、时区、默认标记、可见 / 启用状态以及当前用户可用权限（只读、可写、管理）。即使 P0 UI 只有一个默认日历，也应提供此工具，避免将主 AI 与单日历实现绑定。

### 10.4 `calendar_list_events`

参数示例：

```json
{
  "start": "2026-11-17T00:00:00+08:00",
  "end": "2026-11-18T00:00:00+08:00",
  "timeZone": "Asia/Singapore",
  "calendarIds": ["cal_work"],
  "keyword": null,
  "statuses": ["confirmed", "tentative"],
  "limit": 100,
  "cursor": null
}
```

规则：`start < end`；范围为 `[start, end)`；支持日历、关键词和状态筛选；有最大返回量和分页；按开始时间升序返回；默认不返回已取消事件，除非显式要求；只返回有权访问的数据。

### 10.5 `calendar_get_event`

参数：

```json
{ "eventId": "evt_01JXYZ" }
```

返回事件详情、版本号、重复系列摘要、提醒和关联对象。不存在或无权访问时采用统一错误策略，不泄露其他用户数据。

### 10.6 `calendar_create_event`

参数示例：

```json
{
  "calendarId": "cal_work",
  "title": "产品需求评审",
  "startAt": "2026-11-20T15:00:00+08:00",
  "endAt": "2026-11-20T16:00:00+08:00",
  "allDay": false,
  "timeZone": "Asia/Singapore",
  "description": null,
  "location": null,
  "meetingUrl": null,
  "status": "confirmed",
  "visibility": "private",
  "attendees": [],
  "recurrence": null,
  "reminders": [{ "method": "in_app", "minutesBefore": 10 }],
  "relations": [{ "type": "project", "id": "project_456" }],
  "requestId": "req_abc123"
}
```

规则：

- 未提供 `calendarId` 时，先调用 `calendar_list_calendars`，再选择默认日历或追问。
- 定时事件必须同时提供 `startAt` 和 `endAt`；全天事件必须提供 `startDate` 和 `endDateExclusive`。
- 时间或日期有实质性歧义时先追问。
- 用户明确指定的提醒优先；未指定则继承用户 / 日历默认值；无默认值时不伪造提醒。
- `attendees` 仅表达参与者引用，不代表发送了邀请。
- `relations` 只接受白名单类型和真实对象 ID。
- 存在冲突时返回冲突，不静默覆盖。
- 写入成功必须以服务端返回的 `eventId` 和规范化事件为准。

### 10.7 `calendar_update_event`

参数示例：

```json
{
  "eventId": "evt_01JXYZ",
  "expectedVersion": 1,
  "patch": {
    "startAt": "2026-11-20T15:30:00+08:00",
    "endAt": "2026-11-20T16:30:00+08:00"
  },
  "recurrenceScope": "this_event",
  "requestId": "req_def456"
}
```

规则：

- 修改前先调用 `calendar_get_event` 获取最新版本。
- `patch` 只包含用户明确要求修改的字段。
- “推迟半小时”应保留原持续时长并平移起止时间。
- 不得覆盖用户最近一次并发修改；版本不匹配时重新读取并判断。
- 重复事件必须明确 `this_event`、`this_and_following` 或 `entire_series`；不明确时追问。
- 更新会议链接、参与者或共享可见性等敏感字段，执行相应权限策略。

### 10.8 `calendar_delete_event`

参数示例：

```json
{
  "eventId": "evt_01JXYZ",
  "recurrenceScope": "this_event",
  "expectedVersion": 1,
  "requestId": "req_ghi789"
}
```

规则：

- 先定位唯一事件并读取最新版本。
- 普通单次事件按用户明确指令和全局确认策略执行。
- 删除重复系列、此后全部或批量删除，必须说明影响范围并确认。
- 删除本地记录不等于向参会者发送取消通知。
- 支持软删除 / 恢复时，返回实际删除范围和可恢复状态。

### 10.9 `calendar_check_conflicts`

参数示例：

```json
{
  "startAt": "2026-11-20T15:00:00+08:00",
  "endAt": "2026-11-20T16:00:00+08:00",
  "timeZone": "Asia/Singapore",
  "calendarIds": ["cal_work", "cal_personal"],
  "excludeEventId": null
}
```

返回 `hasConflict`、冲突事件摘要、冲突起止区间。只检测日历中记录的时间重叠，不分析通勤、精力或优先级。

### 10.10 `calendar_find_free_slots`

参数示例：

```json
{
  "rangeStart": "2026-11-23T09:00:00+08:00",
  "rangeEnd": "2026-11-27T18:00:00+08:00",
  "timeZone": "Asia/Singapore",
  "durationMinutes": 60,
  "calendarIds": ["cal_work"],
  "workingHours": {
    "monday": [{ "start": "09:00", "end": "18:00" }],
    "tuesday": [{ "start": "09:00", "end": "18:00" }],
    "wednesday": [{ "start": "09:00", "end": "18:00" }],
    "thursday": [{ "start": "09:00", "end": "18:00" }],
    "friday": [{ "start": "09:00", "end": "18:00" }]
  },
  "bufferBeforeMinutes": 10,
  "bufferAfterMinutes": 10,
  "excludeEventIds": [],
  "limit": 10
}
```

返回候选起止时间、时区和满足约束的说明。只返回空档，不自动创建事件。工作时间和缓冲规则若未配置，主 AI 不得把默认值伪装成用户偏好。

### 10.11 统一响应结构

成功：

```json
{
  "ok": true,
  "data": {},
  "meta": {
    "requestId": "req_abc123",
    "source": "calendar",
    "generatedAt": "2026-11-16T13:00:00+08:00"
  }
}
```

失败：

```json
{
  "ok": false,
  "error": {
    "code": "TIME_CONFLICT",
    "message": "该时间段存在重叠日程",
    "details": [],
    "retryable": false
  },
  "meta": { "requestId": "req_abc123", "source": "calendar" }
}
```

`error.code` 是稳定程序契约；自然语言 `message` 仅用于展示和辅助说明。不得返回数据库 SQL、堆栈或绝对本地路径。

## 11. AI 提示词、上下文与协作规范

### 11.1 提示词集成原则

日历提示词是主 AI 系统提示词中的可组合能力片段，不是一个完整独立 System Prompt。建议资料按职责拆分：

- `calendar-system-prompt.md`：日历能力系统提示词片段。
- `calendar-context-schema.md`：动态上下文结构。
- `calendar-tool-manual.md`：工具调用和操作手册。
- `calendar-tool-schema.ts`：工具 Schema 单一真源或其生成来源。
- `calendar-error-codes.md`：稳定错误码及恢复策略。

实际落盘位置由主 AI 助理模块确定。工具名称、参数字段、错误码与提示词必须从统一契约维护，禁止出现提示词允许调用但 Tool Registry 未注册的情况。

### 11.2 日历系统提示词片段（可集成）

```text
你具备个人助理中的日历工具能力。日历组件是一个确定性的日程数据服务，不是独立 AI Agent。你负责理解用户请求并调用已注册的日历工具；你不直接访问数据库、文件系统或 Electron API。

【职责】
1. 理解用户对日程查询、创建、修改、删除、重复安排、提醒、冲突和空闲时间的请求。
2. 使用系统注入的当前时间、用户时区、日历偏好和权限上下文理解相对日期。
3. 需要事实时先查询工具，不凭对话记忆猜测当前日程。
4. 对目标事件、日期、时间、时长、日历或重复范围存在实质性歧义时先追问。
5. 结合任务、项目、联系人、邮件和文件等模块时，调用对应模块工具，不复制其权威业务数据。
6. 所有写入结果以 Calendar Tool 返回的数据为准；工具失败时不得声称成功。

【时间规则】
1. 相对日期必须以系统注入的 currentDateTime 和 timeZone 为准。
2. 写入定时事件必须使用包含时区偏移的 ISO 8601，并保留 IANA 时区。
3. 全天事件使用 startDate / endDateExclusive，不伪造成午夜定时事件。
4. 时间区间采用 [start, end)，首尾相接不构成冲突。
5. 不得编造开始时间、结束时间、持续时长、地点、参与者或提醒偏好。
6. 用户只说“下午”“下周”等不够精确时，结合明确配置；仍有歧义则追问。
7. 重复事件必须说明频率、开始日期和结束条件；修改必须明确单次、此后或整个系列。

【查询规则】
1. 回答某天或某段时间有什么安排前，必须查询对应时间范围。
2. 修改或删除前，必须查询并唯一定位目标，必要时读取最新事件和版本。
3. 多个同名 / 相近事件不可凭主观相似度选择，必须列出候选并追问。
4. 空闲时间只代表参与计算的可访问日历中没有已记录的占用，不代表现实中绝对空闲。
5. 只展示当前任务需要的信息，不泄露无关私密日程。

【写入规则】
1. 用户明确要求且信息完整时，按全局权限和确认策略执行。
2. 创建前校验必填字段、时间合法性、目标日历和必要冲突。
3. 有冲突时不静默覆盖、不擅自移动其他事件；应说明冲突并提出候选方案。
4. 修改时只改用户明确要求的字段，使用最新版本和幂等请求 ID。
5. 删除重复系列、批量操作、对外邀请或取消通知等高影响操作必须明确确认。
6. 工具失败按稳定错误码处理；只有明确可安全重试时才重试，并沿用原幂等键。

【边界】
1. 不在日历模块内执行长期目标规划、每日简报、周期复盘、时间画像或通用自动化策略；这些由主 AI 统一处理。
2. 不把任务状态、项目进度、联系人联系方式或文件正文复制进日历作为权威数据。
3. 不声称检查过未接入或未授权的数据源。
4. 不把日历无记录解释为用户现实中一定有空。
5. 不因创建本地事件而默认向任何人发送邀请或邮件。

【回复要求】
1. 查询结果按用户本地时间排序并标明日期、时区和全天状态。
2. 创建成功说明标题、日期、起止时间、所属日历和已配置提醒。
3. 修改成功说明实际变更字段。
4. 删除成功说明删除对象和作用范围。
5. 候选空闲时间应说明查询范围及限制，不将候选说成已预约。
6. 只有工具返回成功时才使用“已创建 / 已修改 / 已删除”等完成表述。
```

### 11.3 意图与工具选择规范

| 用户表达 | AI 意图 | 工具顺序 |
|---|---|---|
| “明天有什么安排？” | 查询日程 | `calendar_list_events` |
| “我有哪些日历？” | 查询日历 | `calendar_list_calendars` |
| “周五下午三点安排产品评审” | 创建日程 | 选日历 → 必要时冲突检查 → `calendar_create_event` |
| “把下午的会推迟半小时” | 修改日程 | 查询 → `calendar_get_event` → 冲突检查 → `calendar_update_event` |
| “取消下周的例会” | 删除 / 取消 | 查询候选 → 澄清系列范围 → `calendar_delete_event` |
| “下周找一小时空档” | 空闲查询 | `calendar_find_free_slots` |
| “这个会和什么冲突？” | 冲突查询 | 读取目标事件 → `calendar_check_conflicts` |
| “把这个任务安排到日历” | 跨模块排期 | 读取任务 → 空闲查询 → 用户确认策略 → 创建并关联 |
| “把周会改成每两周一次” | 修改重复规则 | 读取事件 → 澄清生效范围 → 更新系列 |
| “今天会议要准备什么？” | 会议准备 | 查询事件 → 读取关联任务 / 文件 / 知识库 |

```json
      "currentDateTime": "2026-11-16T13:00:00+08:00",
      "timeZone": "Asia/Singapore",
      "locale": "zh-SG",
      "weekStartsOn": "monday"
    },
    "preferences": {
      "defaultCalendarId": "cal_default",
      "defaultEventDurationMinutes": 30,
      "defaultReminderMinutes": 10,
      "workingHours": null,
      "bufferBeforeMinutes": null,
      "bufferAfterMinutes": null
    },
    "permissions": {
      "canRead": true,
      "canCreate": true,
      "canUpdate": true,
      "canDelete": true,
      "canManageCalendars": true,
      "canSendInvitations": false,
      "confirmationRequiredForSeriesDeletion": true
    },
    "availableCalendars": [
      {
        "calendarId": "cal_default",
        "name": "我的日历",
        "timeZone": "Asia/Singapore",
        "isDefault": true,
        "canRead": true,
        "canWrite": true
      }
    ],
    "relevantEvents": []
  }
}
```

注入要求：

- `currentDateTime` 由宿主系统每次动态提供。
- `timeZone` 来自用户设置或系统授权配置。
- 工作时间、默认时长、提醒、缓冲值未设置时省略或标记为 `null`，不得伪装成偏好。
- `permissions` 由宿主和服务端决定，不能接受模型自行提升权限。
- `availableCalendars` 仅包含当前用户有权访问的日历及其能力。
- `relevantEvents` 只提供当前任务需要的最小摘要，不把全部日历历史放入固定上下文。
- 会议链接、私密描述、联系方式和敏感附件信息默认不注入；必要时再按权限读取。
- 工具最新返回的数据优先于旧会话摘要。

### 11.5 上下文更新策略

| 事件 | 更新规则 |
|---|---|
| 用户询问某天安排 | 重新查询该日期范围，不用过期缓存作为事实 |
| 创建成功 | 将返回的事件 ID、规范化时间和版本写入会话短期上下文 |
| 修改成功 | 更新当前会话中相关事件字段和版本 |
| 删除成功 | 将事件标记为已删除，不再作为有效安排引用 |
| 版本冲突 | 重新读取最新事件，再由 AI 判断是否重试 |
| 用户修改时区 / 偏好 | 更新用户设置并在后续请求重新注入 |
| 日历被归档 / 禁用 | 更新可访问日历集合，停止将其视为默认目标 |
| 外部日历断开 | 更新数据源权限和可访问范围 |

## 12. AI 日历使用手册

### 12.1 创建日程

标准流程：

1. 提取标题、日期、起止时间或时长、目标日历、时区、地点、参与者、提醒、重复规则和关联对象。
2. 从当前上下文解析相对日期。
3. 检查必填字段；会改变安排含义的信息缺失时先询问。
4. 需要确定目标日历时调用 `calendar_list_calendars`。
5. 确认重复规则和时长语义。
6. 对重要时间段调用 `calendar_check_conflicts`。
7. 按确认策略调用 `calendar_create_event`。
8. 只在返回成功后告知用户创建完成。

### 12.2 查询日程

- “今天 / 明天 / 本周 / 某天”先转换为用户时区的明确范围。
- 查询结果按开始时间升序排列。
- 全天事件单独标识。
- 区分 `confirmed`、`tentative` 和 `cancelled`。
- 空结果表述为“当前可访问的日历中没有查到记录”，不能断言用户完全空闲。

### 12.3 修改日程

- 修改前查询并唯一定位目标事件。
- “延后半小时”保留原持续时长并整体平移。
- “改到下午三点”若日期和持续时长可从原事件明确继承则保留，否则追问。
- 检查拟定时间的冲突。
- 重复事件必须明确仅本次、此后全部或整个系列。
- 提交 `expectedVersion`；版本冲突后重新读取。
- 修改成功后使用返回的数据确认结果。

### 12.4 删除或取消日程

- 删除前确认目标事件唯一。
- “取消”可能是本地状态改为 cancelled，也可能是删除本地记录，或向参会者发送外部取消通知；语义不清时先询问。
- 删除重复系列或批量影响事件前明确说明范围并确认。
- 删除接口成功后，准确说明是单次实例还是整个系列。
- 本地删除不等于发出外部取消邮件。

### 12.5 查找空闲时间

1. 确定日期范围、连续时长和时间偏好。
2. 确定需要参与计算的日历 ID。
3. 读取用户真实工作时间和缓冲配置；没有配置时不擅自假设。
4. 调用 `calendar_find_free_slots`。
5. 返回带日期、起止时间和时区的候选项。
6. 说明候选只基于当前可访问的日历数据。
7. 没有候选时，说明约束并询问是否扩大范围或调整时长。
8. 用户确认具体时间后，才创建事件。

### 12.6 重复事件操作

| 用户表达 | 作用范围 | 处理要求 |
|---|---|---|
| “这次会议改到周四” | `this_event` | 只修改本次实例 |
| “从下周开始都改到周四” | `this_and_following` | 确定生效日期后执行 |
| “以后每周会议都改到周四” | `entire_series` | 展示影响范围并确认 |
| “取消这周例会” | `this_event` | 只取消本周实例 |
| “以后不再开这个例会” | `entire_series` | 明确确认终止整个系列 |

### 12.7 提醒配置

- 用户明确指定提醒时按本次要求设置。
- 未指定时优先使用用户或日历默认提醒。
- 无默认值时不得声称已经设置提醒。
- 事件改期或删除后，由服务端 / 调度器同步更新提醒任务。
- 通知调度未接通时，不得声称已保证通知送达。

### 12.8 跨模块关联

- 关联任务前先从任务模块读取真实 `taskId`。
- 关联项目前从项目模块读取真实 `projectId`。
- 参与者联系人必须来自联系人模块，不根据姓名猜测邮箱。
- 文件、邮件和知识库内容通过稳定 ID 引用，不复制全文。
- 关联失败时应说明日程本身是否创建成功、关联是否失败，不得将部分成功表述为全部成功。

### 12.9 错误处理

按稳定错误码处理：

- `EVENT_NOT_FOUND`：重新检索或请求用户提供更多定位信息。
- `CALENDAR_NOT_FOUND`：重新查询日历列表。
- `TIME_CONFLICT`：展示冲突并提供候选方案，不擅自覆盖。
- `VERSION_CONFLICT`：读取最新数据并重新判断。
- `TIMEZONE_AMBIGUOUS`：向用户展示歧义并询问。
- `PERMISSION_DENIED`：停止操作，不尝试绕过。
- `DUPLICATE_REQUEST`：返回原请求结果，不重复执行。
- `SERVICE_UNAVAILABLE`：如实说明尚未完成；不能把请求发出当作写入成功。

## 13. 提醒与通知机制

### 13.1 职责划分

- 日历保存提醒规则及其与事件的关系。
- 调度器负责在正确时间触发提醒任务。
- 通知呈现优先复用项目已有通知 / Toast / Electron Notification 能力。
- 若项目当前没有可复用的持久调度服务，可在 Main 进程增加 `CalendarReminderScheduler`，不因此开发通用自动化引擎。
- 若未来有统一通知中心，日历应通过稳定事件消息或任务接口接入，由通知中心负责渠道、重试和送达状态。

不得假设当前项目已经具备统一持久通知中心；开发前必须核对实际实现。

### 13.2 调度要求

- 应用启动时恢复尚未完成的提醒任务。
- 事件新增、修改、取消和删除时同步更新提醒。
- 提醒触发必须幂等，应用重启或定时器重建不重复触发同一事件实例。
- 处理时区变化、事件改期、重复系列实例和过期提醒。
- Renderer 页面定时器不能作为唯一提醒机制。
- 长时间未来提醒应分批调度，避免依赖单个超长 timeout。
- 可靠调度状态应持久化，并记录触发时间和结果。

### 13.3 应用运行状态限制

- 应用窗口关闭但应用在系统托盘持续运行时，Main 进程可继续提醒。
- 用户真正退出应用、进程被系统结束或设备关机时，纯进程内调度无法保证触发。
- 首期必须明确此限制，不宣称应用彻底退出后仍保证通知。
- 系统级定时能力需另行评估，不直接引入常驻服务。

## 14. 跨模块协作规范

### 14.1 M27 速记页

- 仅在左区顶部工具行增加日历入口。
- 不把笔记树、任务清单或画布便利贴自动复制为日历事件。
- 日历关闭后恢复 M27 原状态。
- 稳定任务 / 笔记 ID 可用后，通过 `calendar_event_links` 建立关联。

### 14.2 任务模块

任务模块是任务标题、状态、优先级、负责人、预计耗时和截止日期的权威来源。日历保存 `taskId` 关联，不复制任务状态。

主 AI 在安排任务时，先读取任务，再查询日历空档，最后在确认策略允许时创建日程并建立关联。

### 14.3 项目模块

项目模块管理里程碑、阶段、依赖和进度。日历只保存项目 ID 引用及事件时间，不维护项目状态副本。

### 14.4 联系人模块

参与者使用 `contactId` 关联。姓名匹配不唯一时应澄清。邮箱和手机号必须由联系人模块提供，AI 不得推测联系方式。邀请发送由独立服务负责。

### 14.5 邮箱 M25

首期不因创建日程而自动发送邮件，也不默认发会议邀请。后续如需邮件协作，主 AI 必须明确调用邮箱模块发信工具并遵循邮件模块的发送确认策略。日历只保存邮件关联 ID 或会议链接。

### 14.6 剪藏与本地文件 M26 / 文件查看器

日历可引用剪藏、文件或知识库条目 ID。文件正文解析和检索由对应模块负责。不得复制文件全文进日历数据库，也不得将不受信任内容作为 HTML 直接渲染。

### 14.7 通知与主 AI

日历产生提醒配置和事件变更；通知服务负责投递及状态；主 AI 可在用户授权下生成自然语言提醒或安排摘要。AI 不可伪造通知送达状态。

## 15. 权限、安全、隐私与审计

### 15.1 安全边界

- Main 进程是日历业务数据唯一可信访问边界。
- Renderer 仅通过 Preload 暴露的受控 API 访问日历。
- Provider Child 不得直接连接 `urchin.db`。
- AI Tool Router 使用白名单工具，不提供任意 SQL / 文件系统能力。
- UI 与 AI 的所有写操作都经过同一个 CalendarService 规则校验。
- 所有操作以当前应用用户 / 配置上下文为权限边界；模型不能自行指定用户 ID 绕过鉴权。

### 15.2 操作确认矩阵

| 操作 | 默认策略 |
|---|---|
| 查询日历 / 事件 | 授权范围内无需额外确认 |
| 查询空闲时间 | 无需额外确认，但不泄露他人私密事件 |
| 创建明确的个人单次事件 | 用户明确提出且字段完整时可执行并反馈 |
| 创建时间 / 时长不明确事件 | 先追问或展示待确认方案 |
| 修改唯一且明确的单次事件 | 用户明确要求时可执行，执行后反馈 |
| 删除单个个人事件 | 按全局风险策略；可配置确认与撤销 |
| 修改 / 删除重复系列 | 必须明确范围；范围性变更确认 |
| 批量修改 / 删除 | 必须说明影响数量和范围并确认 |
| 修改共享日历 | 按权限和影响等级确认 |
| 发送外部邀请 / 取消通知 | 必须单独确认；首期不启用 |

### 15.3 隐私要求

1. 默认本地保存日历数据。
2. 只将当前任务所需的最少字段发送给模型。
3. 私密描述、会议链接、参与人联系方式和敏感附件不默认进入上下文。
4. 共享场景按权限隐藏私密标题或详情。
5. 日志避免记录事件描述全文、私人地点、完整 Prompt 和凭据。
6. 外部日历授权必须说明数据流向、权限范围和撤销方式。
7. 用户应能查看 AI 对日历执行的关键操作。
8. 不根据日程推断或展示用户健康、情绪、宗教、政治等敏感属性。

### 15.4 审计字段

至少记录：

- 操作主体 / 来源（UI、AI、导入、系统）。
- requestId、操作时间、操作类型。
- 目标 calendarId / eventId。
- 必要变更摘要及版本号。
- 幂等键和执行结果。
- 错误码（若失败）。

审计应支持问题追踪和必要恢复，但不应无限制保存完整私密日程内容。

### 15.5 撤销与恢复

- 对可逆更新保存必要的变更前快照或版本信息。
- 删除采用软删除或可恢复回收策略，产品需明确保留期限。
- 撤销操作必须检查事件当前版本，避免把后续新修改覆盖掉。
- 外部同步或已发送通知等副作用不保证能够通过本地撤销自动逆转，必须单独提示。

## 16. 错误码与异常处理

| 错误码 | 含义 | 调用层处理 |
|---|---|---|
| `INVALID_ARGUMENT` | 参数缺失、类型或格式错误 | 修正参数；缺信息时追问 |
| `INVALID_TIME_RANGE` | 结束不晚于开始或查询范围无效 | 检查起止时间和时区 |
| `TIMEZONE_AMBIGUOUS` | 本地时间存在时区 / 夏令时歧义 | 展示歧义并询问 |
| `TIME_CONFLICT` | 与已有事件时间重叠 | 返回冲突事件，供 AI 提出方案 |
| `EVENT_NOT_FOUND` | 事件不存在或不可访问 | 重新检索，不泄露他人数据 |
| `CALENDAR_NOT_FOUND` | 日历不存在或不可访问 | 重新查询日历列表 |
| `PERMISSION_DENIED` | 当前主体无相应权限 | 停止操作，不尝试绕过 |
| `VERSION_CONFLICT` | 数据已被其他操作修改 | 读取最新数据后重新判断 |
| `DUPLICATE_REQUEST` | 幂等请求重复 | 返回原操作结果，不重复创建 |
| `RECURRENCE_INVALID` | 重复规则无效或组合不支持 | 修正规则或向用户澄清 |
| `RECURRENCE_SCOPE_REQUIRED` | 重复事件操作缺少作用范围 | 询问仅本次、此后或整个系列 |
| `RELATION_NOT_FOUND` | 关联对象不存在或不可访问 | 不写入无效关联，告知部分失败 |
| `REMINDER_UNAVAILABLE` | 当前通知渠道 / 调度不可用 | 明确说明日程已保存但提醒未启用 |
| `RATE_LIMITED` | 请求频率超限 | 按 retryAfter 有限等待 |
| `SERVICE_UNAVAILABLE` | 服务暂时不可用 | 安全重试或说明未完成 |
| `STORAGE_ERROR` | 数据库读写或 migration 错误 | 记录 requestId，停止写入并报告 |
| `INTERNAL_ERROR` | 未预期错误 | 记录 requestId，不暴露内部细节 |

处理原则：

- 错误码稳定，不用自然语言 message 做程序分支判断。
- 只有明确可重试且具备幂等保护的操作才自动重试。
- 写请求重试必须沿用原幂等键。
- 工具失败时 AI 应区分“未执行”“执行结果未知”和“执行成功”。
- 部分成功时明确指出成功部分和失败部分，例如事件已创建但关联文件失败。

- Renderer 不维护可独立写入的长期日历副本。
- 打开窗口时按当前视图查询范围加载事件；切换日期或月份增量查询。
- 写操作成功后使用 Main 返回的规范化数据更新 UI。
- 多视图一致性通过事件变更通知和重新查询保持，不以 Renderer 缓存作为权威数据。

### 17.5 领域事件

建议事件名：

- `calendar.event.created`
- `calendar.event.updated`
- `calendar.event.deleted`
- `calendar.event.cancelled`
- `calendar.reminder.scheduled`
- `calendar.reminder.fired`
- `calendar.calendar.updated`

事件负载仅包含 eventId、calendarId、版本、变更类型、发生时间和必要元数据，默认不携带完整私密描述。

### 19.1 单元测试

至少覆盖：

- Schema 校验和默认值。

- Repository CRUD、migration 和事务回滚。

- 乐观锁与版本冲突。
- 关联对象校验和部分失败处理。
- 提醒触发去重、改期更新和应用启动恢复（P1）。
- 软删除、恢复和审计记录。

### 19.2 IPC 与 AI Tool 测试

- IPC 请求和响应均通过 Zod Schema。
- 未授权事件无法读取、修改或删除。
- Tool 参数不能自行传入并决定 `ownerId`。
- `calendar_list_calendars` 返回权限和默认日历信息。
- 创建事件支持 `recurrence`、`reminders`、`attendees` 和 `relations` 参数契约。
- 更新 / 删除重复事件必须提供作用范围。
- 空闲查询只返回符合约束的候选时段。
- 同一幂等键重复调用不会创建重复事件。
- `VERSION_CONFLICT` 能引导重新读取。
- 错误响应不泄露数据库细节。
- Mock Tool Host 能覆盖核心工具执行与失败流程。

### 19.3 E2E 测试

必须覆盖：

1. 打开 `urchin://notebook`，确认日历图标出现在左区顶部“+”按钮左侧。
2. 验证“+”原功能完全不变。
3. 点击日历入口打开模态窗口。
4. 关闭按钮、Esc 和遮罩关闭按预期工作；未保存数据有保护。
5. 窗口打开和关闭后，当前笔记、页面树、画布、滚动位置和分割比例保持不变。
6. 新建、查看、编辑和删除普通事件。
7. 全天和跨天事件显示正确。
8. 月份切换、今天按钮、筛选和主题切换正常。
9. 应用重启后事件数据仍存在。
10. 多日历和周 / 日视图在 P1 实现后覆盖。
11. 重复事件单次、此后和整个系列操作在 P1 实现后覆盖。
12. 提醒在事件改期和删除后正确更新，且不重复触发。
13. AI Tool Mock 完成日历列表、查询、创建、更新、删除、冲突和空闲查询调用。
14. AI 工具失败时显示正确错误，不把失败操作误报为成功。

### 19.4 项目质量门禁

遵循仓库最新 `AGENTS.md` 和工程规范：

- 每次实现改动后运行 `pnpm verify`。
- UI 改动运行受影响的 Playwright E2E，优先使用项目选择性 E2E 命令。
- 运行 `pnpm build` 并启动应用做实际界面验收。
- 修改 Schema、模块索引或文档时执行项目文档检查。
- 按项目要求更新 CHANGELOG、模块全景、契约索引和必要 ADR。
- 覆盖率门槛以当前 `vitest.config.ts` 和项目技术规范为准。

### 19.5 质量指标

| 指标 | 定义 | 目标用途 |
|---|---|---|
| 事件创建成功率 | 合法创建请求中成功持久化比例 | 基础写入可靠性 |
| 核心查询响应时间 | 事件查询 P50 / P95 | UI 与 AI 响应体验 |

## 20. 风险、限制与实施前决策

### 20.1 主要风险

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 把事件数据写入 `notebook.state` | M27 耦合、查询困难 | 使用 M8 结构化表 |
| Renderer 直接访问数据库 | 安全和一致性风险 | Main Service + IPC |
| AI 直接操作数据库 | 越权、数据损坏 | Tool 白名单和受控路由 |
| 日期时区规则分散 | 事件时间偏移 | CalendarService 统一时间处理 |
| 重复规则不明确 | 错误修改单次或整个系列 | 明确 scope 并测试例外 |
| Tool 与数据模型脱节 | AI 无法使用已存储能力 | 契约覆盖 recurrence / attendees / relations |
| Provider 不支持 function calling | 某些模型无法原生调用工具 | 主 AI Tool Gateway 适配 |
| 提醒重复或漏触发 | 用户错过重要安排 | 持久调度、幂等和启动恢复 |
| 并发写入覆盖 | 用户修改丢失 | expectedVersion 乐观锁 |
| 外部同步冲突 | 数据不一致 | P2/P3 独立集成适配器 |
| 日历窗口破坏 M27 | 速记体验退化 | Modal 隔离、状态保持 E2E |
| 备份不完整 | 日历数据不可恢复 | 定义备份范围并做恢复演练 |

### 20.2 首期明确不支持

- 不保证应用完全退出、进程被结束或设备关机时仍能触发本地提醒。
- 不自动向联系人发送会议邀请或邮件。
- 不在 P0 完成 Google / Outlook / CalDAV 同步。
- 不在 P0 提供多用户共享日历和团队协作。
- 不建设独立日历 AI Agent、自动化引擎或时间数字孪生。
- 不承诺 AI 可以访问用户未授权的外部账户或数据源。
- 不把空闲时段查询结果解释为现实世界绝对可用。

### 20.3 实施前需要确认的事项

进入详细排期前，由产品和研发负责人确认：

1. 当前仓库可用的 M28 模块编号及文档编号。
2. 首期只运行桌面端还是计划同时支持 Web / 移动端。
3. 当前主 AI Tool Registry 是否已可用；若未就绪，Mock Host 的接口边界如何定义。
4. 当前是否已有 Main 端通知调度能力；如无，首期提醒范围如何界定。
5. 用户默认时区取应用设置还是操作系统设置。
6. 删除采用软删除、回收站还是版本化恢复，以及保留期限。
7. 重复规则采用内部结构化规则还是第三方 RRULE 库。
8. P1 的任务、项目、联系人、邮件和文件模块是否已有稳定 ID / API。
9. P2 外部日历同步优先顺序与授权策略。
10. 日历数据备份是否并入 Urchin 现有备份能力，还是提供专门导出。

没有明确的依据时，不应在文档中宣称相应模块或服务已经存在。

## 21. 最终建设决策与交付清单

### 21.1 最终建设决策

Urchin Browser 的智能日历按 **M28 Calendar 本地时间与日程基础能力组件**建设。

1. **入口**：在速记页左区顶部，现有“+”按钮左侧增加日历图标。
2. **窗口**：打开速记页内模态日历窗口；关闭后完整保留 M27 状态。
3. **数据**：复用 M8 主 SQLite 数据库 `urchin.db`；不将事件放入 `notebook.state` 或 `ai.db`。
4. **架构**：Main 进程 CalendarService；Renderer 通过 Preload / M17 typed IPC 调用。
5. **界面**：P0 实现月视图、Agenda、事件详情和 CRUD；P1 增加周 / 日视图和多日历管理 UI。
6. **领域模型**：P0 预留完整多日历、重复事件、参与者、会议链接、提醒和关联字段；按 P0–P3 分阶段启用。
7. **AI 工具**：保留完整 `calendar_*` 工具契约，包括 `calendar_list_calendars` 和重复、参与者、关联字段；AI 通过统一 Tool Gateway 调用。
8. **AI 资料**：P0 交付提示词片段、上下文 Schema、意图与工具选择表、操作手册和错误码规范。
9. **智能能力**：自然语言理解、全局排期、每日简报、周期复盘、主动服务由主 AI 负责。
10. **时间规则**：CalendarService 统一处理时区、全天、跨天、重复、冲突和空闲计算。
11. **提醒**：日历管理提醒配置；P1 实现持久调度及通知联动，并明确应用退出限制。
12. **扩展**：外部同步、邀请、共享和多端协作按 P2/P3 单独建设。
13. **质量**：遵循项目工程门禁、测试、文档索引、CHANGELOG 和 ADR 约束。
