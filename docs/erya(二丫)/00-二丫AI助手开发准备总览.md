二丫是顽童浏览器的原生 AI 助手。它接收用户目标，调动浏览器功能，给出有依据的建议，并在用户设定的权限内完成任务。用户决定目标、数据范围和授权，二丫负责规划、执行、核验与整理经验。

版本：v0.4 评审草案。日期：2026年11月16日。原始审查基线 `7f9f59a`；速记、日历、邮箱及本轮F12增量核对按提交 `f92816c327cab6978838a860ccddddf26a30e942` 增量核对。这套资料包含12份开发前文档及交互原型；新增产品规则、接口和数据表均为设计方案，尚未实施。

## 先看这三个结论

**二丫独立于 Pi。** 当前项目已有 Electron、Chromium、React、TypeScript、SQLite 和多种浏览器模块。此前已完成入口占位和部分设置分离，仍有旧 `ai.*` 调用与存储引用；全面切割尚未完成。用户已确认二丫使用 `erya.*`，原 `ai.*` 是二丫前身 AI 助手的预留命名，不属于 Pi。旧引用清理是二丫落地的前置工作。

**按批次完成可靠闭环。** A批先做选定网页 → 比较建议 → 确认写书签或笔记 → 回读 → 受控记忆；B批为速记与日历；C批为邮箱和邮件转笔记、任务、日程。批次用于逐步验收，速记、日历、邮箱均在当前任务范围。

**把仿生记忆转成可管理的工程机制。** 区分临时上下文、长期事实与偏好、可复用流程；设置容量和期限，支持纠正、遗忘、去重与压缩。升级通过版本化评测和回退实现，模型不能自行扩大权限或改写已发布程序。

## 用简单的话理解权限

| 档位        | 二丫可以做什么                           | 例子                             |
| ----------- | ---------------------------------------- | -------------------------------- |
| L0 对话     | 只看你主动给它的内容                     | 解释一段文字，写一份草稿         |
| L1 范围读取 | 读取你选择的页面或资料                   | 比较这三个标签页                 |
| L2 确认执行 | 每次改动前让你看清楚并确认               | 把这段结论存为笔记               |
| L3 有限自主 | 在你规定的对象、期限和额度内做低风险操作 | 在指定收藏夹内整理本次选中的条目 |

建议首版实现 L0—L2，L3 放在后续阶段。发信、付款、不可恢复删除、凭据与权限变更等高风险操作保留逐次确认。你可以撤销后续授权；已经产生的外部结果能否撤回，取决于对应功能是否支持撤销。

能读某个网页，不等于能把它发给在线 AI；能写笔记，不等于能访问全部工作区。每项授权都需要说明范围和期限。

## 开发前需要解决的五个技术问题

| 问题                        | 实际影响                                   | 准备工作                                                   |
| --------------------------- | ------------------------------------------ | ---------------------------------------------------------- |
| 旧 `ai.*` 上下游仍有耦合    | 改前缀后仍可能保留错路由、旧入口与混合存储 | 先完成 CUT-01 全面切割，含调用链、数据迁移、文档和回归门禁 |
| 当前模型契约偏聊天          | 声明支持工具不等于工具往返已接通           | 定义工具调用编号、工具结果、能力探测和兼容策略             |
| 现有 IPC 校验不等于业务授权 | 参数合法仍可能跨工作区或越权               | 统一执行端权限校验，绑定调用来源和资源范围                 |
| 取消与重试需要真实结果语义  | 取消可能只停止显示，重试可能重复写入       | 实际请求取消、幂等键、回读核验和结果未知状态               |
| 现有模块接口开放程度不同    | 不能通过“全模块支持”一句话实现融合         | 维护功能到工具、权限、验证器的接入矩阵                     |

## 从准备到开发的推进方式

1. **确定第一条验收故事。** 已明确接入速记、日历和邮箱；建议以“比较网页后保存笔记”为A批闭环，再按B、C批逐项接入。

2. **评审原型与权限。** 用演示原型检查自己能否看懂二丫将做什么、怎样停止、记住了什么。

3. **完成切割和最小技术验证。** 先验收 CUT-01 旧命名与上下游清理，再用测试数据接通一个只读工具和一个可验证写工具，证明审批、取消、幂等和核验可行。文档与原型可继续并行完善。

4. **实现首版闭环。** 按 PRD 的 P0 要求补齐记忆、数据隔离、预算与异常处理。模型评测使用同一批固定任务。

5. **逐批接入并验收。** B批速记与日历、C批邮箱与协作，每批同步完善接口、权限、原型和测试。详细依赖及退出条件见[04功能模块与任务安排](./04-二丫功能模块清单.md)。

排期以阶段验收为依据。现阶段没有确认团队投入和模型预算，因此不把完整二丫压成一个固定周数承诺。日常协作中，一次只让产品负责人决定两三个会影响下一步的问题；技术细节由开发方案解释并给出推荐值。

## 下一轮需要你的三个简单决定

| 问题                         | 建议选项                       | 对开发的影响                             |
| ---------------------------- | ------------------------------ | ---------------------------------------- |
| 第一条验收故事               | 建议先比较资料并整理笔记       | 影响演示顺序；速记、日历与邮箱范围已确定 |
| 是否允许在线 AI 处理选定内容 | 可允许，但显示发送范围且可关闭 | 决定提供方、外发策略和本地降级           |
| 最初允许二丫主动到什么程度   | 先建议，写入前确认             | 决定默认权限和主动提醒时机               |

上述建议不会自动成为用户授权。Muse 链接补齐后，再建立参考功能对照表，记录哪些体验适合二丫、哪些需要按顽童浏览器重新设计。

## 术语说明

| 术语       | 简单解释                                         |
| ---------- | ------------------------------------------------ |
| MVP        | 最小可用版本，先把一条完整任务做好               |
| Agent      | 会规划步骤并调用工具的助手执行程序               |
| 工具       | 二丫可调用的具体功能，例如读取网页或创建书签     |
| IPC        | 浏览器不同进程之间的通信接口                     |
| 幂等       | 同一个操作因网络问题重复提交，也只产生一次结果   |
| Token      | 模型计算文本长度和费用时使用的单位，不等于汉字数 |
| 向量索引   | 帮助按意思查找记忆的索引，可选，不等于记忆本身   |
| 灰度与回退 | 先小范围试用新版本，出问题恢复旧版本             |

## 当前接入范围与新增事实

当前接入范围为速记页（笔记本中的任务清单、笔记、画布，以及本地日历）与邮箱页。A批先完成基础MVP，B批接入速记与日历，C批接入邮箱和跨模块协作；B、C均已纳入当前开发准备。GenOffice、DeepSeek Harness、Pi 与二丫的交互分别记为 FUT-GO、FUT-DSH、FUT-PI，当前只留痕待办，未来另行立项。CUT-01旧 `ai.*` 全面切割及原功能回归仍是近期前置任务，不随远期联动后置。

本地日历P0/P1已实现，8个AI工具合同已预留、尚未注册。日历可关联并跳转笔记/任务；邮件引用尚缺可靠解析与跳转。速记整份状态写入需要并发保护；邮箱已有读取和SMTP基础，草稿、稳定引用和发送对账需补齐。新增事实依据：[日历合同](https://github.com/sgobiorodolfo170-ai/Urchin-Browser/blob/f92816c327cab6978838a860ccddddf26a30e942/docs/contracts/L-智能日历.md)、[ADR-023](https://github.com/sgobiorodolfo170-ai/Urchin-Browser/blob/f92816c327cab6978838a860ccddddf26a30e942/docs/decisions/ADR-023-本地日历与预备工具边界.md)。原快照引用保留其历史核对含义。

## 二丫与F12的接入结论

可行，采用“原生F12供用户手动调试，二丫通过受控证据接口诊断”的路线。最新实现已退出旧React面板、持续CDP采集器、8个RPC与2个事件；不能把旧合同当现役二丫接口。仓库[Win11验收报告](https://github.com/sgobiorodolfo170-ai/Urchin-Browser/blob/f92816c327cab6978838a860ccddddf26a30e942/docs/开发者工具P0验收-Win11-2026-11-16.md)记录原生P0通过，Win10候补，P1未启动。

DevTools接入按易到难分为DT-00手动报错解释、DT-01受控证据原型、DT-02按需Console、DT-03网络元数据、DT-04选定DOM/CSS、DT-05隔离样式预览与前后核验、DT-06二丫/Provider/工作区关联诊断。DT-00可在A批基础闭环后增加；自动采集作为C批后的D批限定试验，先做DT-01/02和DT-QA，后续能力在收益与安全门槛通过后逐项启动，不阻塞原A/B/C批。

难点在目标与导航绑定、敏感数据过滤、原生F12与采集器共存及修复验证；不重建通用DevTools、不新增全局调试端口、不恢复旧ai接口。详细论证见[06架构](./06-二丫系统技术架构设计.md)，任务与退出条件见[04](./04-二丫功能模块清单.md)。
