## 服务商映射

- QQ、163、126、Yeah、新浪、139、189、iCloud、Yahoo、AOL：复用现有 ImapFlow/Nodemailer 的账号 + 授权码/应用专用密码认证。各服务商的授权码获取过程仍在官网完成，开源代码不能代为生成。
- 腾讯企业邮、Zoho：密码/专用密码取决于管理员或 MFA 策略，沿用已有条件提示。
- 搜狐、阿里个人邮箱：已有服务器配置保留；上次官方核查仍有待确认项，不能把第三方配置表当作账号登录实测。见[官方复核](./邮箱设置与认证复核.md)。
- Gmail：新增 OAuth2；保留应用密码方式。授权 scope 为 https://mail.google.com/。
- Outlook/Hotmail：新增 OAuth2；只请求 Exchange 的 IMAP.AccessAsUser.All / SMTP.Send 和 offline_access，不混用 Graph 访问令牌。

## 使用方式

在邮箱登录页选择 Gmail 或 Outlook，输入邮箱地址与显示名称，在 OAuth 区域填写应用配置后点击授权登录。应用配置与账号令牌使用现有 SecretStore 加密，渲染层只收到 Client ID 和是否有已存 Secret，不收到已有 Secret 或令牌。

Google Cloud：创建自己的项目和 Desktop app 类型的 OAuth 客户端；填写 Client ID / 桌面客户端的 Client Secret；配置 OAuth 同意屏幕与测试用户。使用系统浏览器及临时 loopback 端口回调，测试模式相关刷新令牌通常7天到期。正式对外分发仍需完成 Google 对邮件受限权限的审核。[官方桌面流程](https://developers.google.com/identity/protocols/oauth2/native-app)。

Microsoft Entra：创建允许个人微软账号的应用；Mobile and desktop applications 注册 http://localhost/callback（loopback 端口按微软规则动态分配）；添加 Office 365 Exchange Online 的 IMAP.AccessAsUser.All / SMTP.Send 委托权限。使用公共客户端 PKCE，不配置客户端 Secret。个人 Outlook 网页需开启 IMAP；企业租户另受管理员同意与 SMTP AUTH 策略约束。[官方邮件OAuth](https://learn.microsoft.com/en-us/exchange/client-developer/legacy-protocols/how-to-authenticate-an-imap-pop-smtp-application-by-using-oauth)。

授权后先验证 IMAP 访问成功再保存账号，SMTP 使用相同 Exchange/Gmail 邮件资源令牌。自动续期会保存轮换后的 refresh token。设置 → 账号 → 重新授权可更新 OAuth 凭据。删除只清理本机账号及令牌，不替用户撤销服务商网页中的应用授权。

## 自审与验证

性能：同一账号并发刷新合并为一个请求；只在到期前刷新。架构：主进程负责授权回调与令牌，IPC 使用 zod 校验；auth_provider 用主库 v7 迁移持久化，旧账号继续走密码。健壮性：state + PKCE、仅 loopback 监听、3分钟超时、token网络请求30秒超时、不把原始令牌错误输出到界面、凭据写入与账户插入失败补偿。

尚无用户自己的 Google/Microsoft Client ID；自动测试只能验证协议和生命周期，不能据此声称真实服务商账号已登录成功。
