# ADR-008 · v0.1 范围与工期权衡：MVP + 强隔离 = 6-8 周

> 状态：Accepted  · 决策日：2026-07-27  · 关联：D7
> 影响范围：Roadmap 节奏、版本里程碑、验收标准

## 决策

Urchin Browser v0.1 范围定为 **MVP 最小闭环 + per-provider 强隔离架构**，实际工期 **6-8 周**（含收口、测试与发布准备）。

- macOS / Linux 平台扩展

## 背景

初始讨论将 v0.1 工期设为 4-6 周 MVP 最小闭环（基于「同进程隔离 + 官方 Provider 限制」假设）。在 IP4/IP8 路径决策时，用户在了解强隔离 + 第三方加载的工程影响（详见 [ADR-004](./ADR-004-AI进程隔离策略.md)）后，选择「接受 6-8 周工期」换取架构纯净度。

## 候选方案

| 方案 | v0.1 工期 | 隔离架构 | 第三方加载 | 技术债 |
|---|---|---|---|---|
| **A. MVP + 强隔离**（采纳） | 6-8 周 | per-provider 子进程 | 允许（warning 流程） | 无 |
| B. MVP + 折中准备态 | 4-6 周 | 同进程 + 保留 spawn 接口 | 允许（弱隔离 warning） | 中（v0.2 迁移） |
| C. MVP + 强隔离 + 不开第三方 | 5-6 周 | per-provider 子进程 | 仅官方预装 | 低 |
| D. MVP 完全同进程 | 4-6 周 | 同进程 | 仅官方预装 | 高 |

## 决策理由

### 采纳方案 A 的理由

1. **架构一次到位**：v0.1 即建立 per-provider fork 接口与心跳协议，v0.2+ 不需要重构主进程的 Provider 调度路径——避免「先同程后续迁移」的双重工程税。
2. **Provider 中立原则的落地**：D5 决策不绑单一 LLM 提供方，per-provider 子进程是这一原则的安全底线。
3. **安全作为差异化点**：Urchin 与商业 AI 浏览器竞品的差异化之一就是「第三方 Provider 在沙箱里跑」，开源生态对接的安全信号。
4. **用户体验**：第三方 Provider crash 不带倒浏览器是 v0.1 就必须保证的底线，不能等 v0.2 修。

### 否决方案 B（折中准备态）

「保留 spawn 接口给 v0.2 迁移」听起来轻量，实际是双重工程税：
- v0.1 写一份同进程调度代码
- v0.2 写一份子进程调度代码
- v0.2 还要写迁移测试与回滚机制

不如 v0.1 一次写到位。

### 否决方案 C（强隔离但不开第三方）

把官方 Provider 也跑在子进程确实更隔离，但失去了 Provider 中立原则的实质——用户自带 LLM 的能力是 Urchin 的核心差异化。开第三方是必须的。

### 否决方案 D（完全同进程）

与 [ADR-004](./ADR-004-AI进程隔离策略.md) 决策根本冲突。

## v0.1 8 周分波计划

| Wave | 工期 | 模块 | 验收信号 |
|---|---|---|---|
| W1 | 1 周 | M1 + M2 + M3 + M17 + M18 | 能打开窗口、多标签、导航 URL、关闭；IPC 类型化；sandbox+contextIsolation 开 |
| W2 | 1 周 | M4 + M5 + M6 + M7 + M10-lite + M19 + M23 基础 | 地址栏输入 + 历史/书签/设置 UI 可用；扩展加载与 manifest 解析（M10-lite）；下载进度/暂停/取消；基础主题切换 |
| W3 | 1.5 周 | M8 + M11 + M12 + M17 token 直通 | SQLite 持久化；Orchestrator fork；Provider API 契约；token 流从 Provider Child 经 Orchestrator 经 Main 中转到达 Side Panel |
| W4 | 1.5 周 | M13 + M14 demo + M15 demo | 1 个官方 Provider（OpenAI 兼容）接入；Side Panel 摘要当前页面正文；DevTools 增强 demo |
| W5 | 1 周 | 第三方 Provider 加载 + UI warning 流程 | 用户能加载本地路径/npm 包 Provider；版本协商失败有清晰错误提示；crash 后 UI 正确降级 |
| W6 | 1 周 | 收口 + 测试 + CI | 单测覆盖率达标；E2E 关键路径跑通；pre-commit hook 启用；GitHub Actions 流水线绿 |
| W7 | 0.5-1 周 | 体验调优 + 文档完善 | 启动 ≤3s；内存 ≤500MB（10 标签）；CHANGELOG 与 README 完善 |
| W8 | 0.5 周 | 发布准备 | electron-builder 打 Windows 安装包；签名（如有证书）；release notes |

## v0.1 验收标准（可机器判定）

按 AGENTS.md §一「目标前置」原则，验收必须是 0/1 信号：

- [ ] `pnpm typecheck` 通过
- [ ] `pnpm lint` 通过
- [ ] `pnpm test --coverage` 达 [03-tech-stack §4](../03-技术栈.md#4-测试覆盖率适配门槛) 阶梯要求（v0.1 整体 ≥60%）
- [ ] `pnpm e2e` 关键路径全绿：启动、开标签、导航、AI 摘要、关标签
- [ ] electron-builder 产出可安装的 Windows 包，签名验证通过（若有证书）
- [ ] 启动时间 ≤3s（10 次冷启动 P95）
- [ ] 内存 ≤500MB（10 标签场景，P95）

## 否决方案理由汇总

- **B 折中准备态**：双重工程税，v0.1 与 v0.2 各写一份调度代码。
- **C 强隔离不开第三方**：失去 Provider 中立原则实质，与 D5 决策冲突。
- **D 完全同进程**：与 ADR-004 决策冲突。

## 后果

### 正面

- v0.1 即建立稳定架构地基，v0.2+ 演进不需重构主路径。
- 第三方 Provider 加载流程上线即满足差异化定位。
- 工程节奏可预测（8 周分波明确）。

### 负面

- 6-8 周比 4-6 周晚 2 周交付。
- v0.1 阶段需要写子进程管理 + 心跳协议 + crash 恢复等基础设施，工作量集中。
- 测试覆盖率门槛在 v0.1 阶段降低为 ≥60%，此后按阶梯逐版本提升（[03-tech-stack §4](../03-技术栈.md#4-测试覆盖率适配门槛)）——这是 AGENTS.md §八允许的适配，但需在 CHANGELOG 注明过渡计划。
