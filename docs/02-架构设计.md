# 02 · 架构设计

> 状态：Draft  · 日期：2026-07-27

## 1. 进程模型

```
┌────────────────────────────────────────────────────────────────────┐
│  Main Process  (SINGLE SOURCE OF TRUTH)                            │
│  ├─ M1  Window Lifecycle                                           │
│  ├─ M2* Tab Manager    ( BrowserView 持有 + 状态源)                │
│  ├─ M3  Navigation Stack                                           │
│  ├─ M5* Bookmarks   M6* History   M7* Settings                    │
│  ├─ M8  Storage Layer ( SQLite + safeStorage )                    │
│  ├─ M9* Chrome API Compat Backend  (PermissionGuard 二次校验)      │
│  ├─ M10 Extension Loader ( v0.1 lite / v0.2+ 完整 )               │
│  ├─ M16 Network Interceptor ( v0.2+ )                             │
│  ├─ M23 Download Manager ( v0.1 基础 )                            │
│  ├─ M17 IPC Router    ( ipcMain.handle + MessagePort 转交 )       │
│  ├─ M18 Permission/Sandbox                                        │
│  └─ M20 Update Service ( v0.3+ )   M21 Crash Reporter ( v0.2+ )   │
└─────┬───────────────────────────┬──────────────────────┬──────────┘
      │ ipcMain.handle            │ MessagePort           │ utilityProcess.fork
      │ / ipcRenderer.invoke      │ (token 直通)           │
      ▼                           ▼                        ▼
┌──────────────────────────┐ ┌──────────────────┐ ┌─────────────────────────┐
│  Renderer Process (UI)   │ │  AI Utility      │ │  AI Orchestrator        │
│  per BrowserWindow       │ │  (per Provider)  │ │  (官方代码，调度/限流)   │
│  ├─ M2* Tab UI 镜像       │ │  Provider Child  │ │  ├─ 调度                │
│  ├─ M4  Omnibox          │ │  ├─ M11 LLM Call │ │  ├─ 限流                │
│  ├─ M5* M7* UI           │ │  ├─ M12 Provider │ │  ├─ 错误重试            │
│  ├─ M13 AI Side Panel    │ │ │   Implementation│ │  └─ 协议转译            │
│  ├─ M14* Context Extract │ │ └─ 第三方 SDK    │ │                         │
│  ├─ M15 DevTools Enhance │ └──────────────────┘ └──────────┬──────────────┘
│  ├─ M17 IPC Client       │        ▲                         │ fork
│  └─ M19 Theme/UI System  │        │ MessagePort ( 两级 )    │
│                          │        └─────────────────────────┘
└──────────────────────────┘
```

### 1.1 进程类型清单

| 类型 | 数量 | 触发 | 崩溃影响 |
|---|---|---|---|
| Main | 1 | 应用启动 | 全应用退出 |
| Renderer (main window) | 每窗口 1 | M1 创建窗口 | 该窗口 UI 挂，主进程不挂 |
| Renderer (BrowserView) | 每 tab 1 | M2 创建 tab | 该 tab 挂，主进程不挂 |
| Renderer (extension background) | 每 extension 1 | M10 加载扩展 | 该扩展挂，其他扩展与浏览器不受影响 |
| AI Orchestrator (utility) | 1 | 应用启动 | AI 功能不可用，浏览器仍可用 |
| Provider Child (utility) | 每 Provider 1 | Provider 被首次调用 | 该 Provider 不可用，Orchestrator 与其他 Provider 不受影响 |

### 1.2 进程拓扑的关键设计

- **Main 不跑陌生人代码**：扩展与 Provider 都不进 Main。
- **Main 不跑 CPU 密集任务**：LLM 流式 token 拼装、向量化等 CPU 密集任务全在 utility 进程。
- **两级 utility fork**：Orchestrator（官方）→ Provider Child（第三方）。这是 D4 + IP4 的落地形态。
- **MessagePort 两级 chain**：Orchestrator ← Provider Child 之间一对，Orchestrator ← Renderer 之间一对经 Main 转交一次。流式 token 走两跳，延迟 ~2-4ms。

## 2. IPC 拓扑

详见 [contracts/B-ipc-protocol](./contracts/B-进程间通信协议.md)。本节给出架构层视角。

### 2.1 双通道设计

| 通道 | 用途 | 协议 | 校验 |
|---|---|---|---|
| **请求-响应 RPC** | 标签/书签/设置/Provider 配置等离散调用 | `ipcMain.handle` / `ipcRenderer.invoke` | 每调用 zod 入参 + 出参双向 parse |
| **流式 MessagePort** | AI token 流 / Provider 事件 / 长任务进度 | `MessagePort.postMessage` | 每条 message zod parse |
| **单向事件推送** | Main → Renderer 推 tab/window 状态变化 | `webContents.send` | 事件 schema zod parse（一次性，在 Main 端发前校验） |

### 2.2 流式链路（Renderer ↔ Orchestrator ↔ Provider Child）

```
[Provider Child] ─postMessage─► [Orchestrator] ─postMessage─► [Main 中转] ─postMessage─► [Renderer Side Panel]
        ▲                                                                                      │
        │ AbortSignal (ipcRenderer.invoke 'ai.chat.abort')                                    │
        └─────────────────── [Renderer UI 中止按钮] ───────────────────────────────────────────┘
```

- 中止链路独立于流式通道，走 RPC `ai.chat.abort`，Orchestrator 转发到 Provider Child 的 `AbortController.abort()`。
- Main 中转一次（IP9 决策）——Main 不解析 token 内容，只 forward；v0.2+ 可优化为 utility 直连 renderer 绕过 Main。

## 3. AI 隔离拓扑

这是 D4 与 IP4-IP8 的具体落地。

### 3.1 三层隔离

```
边界1: 渲染层与 AI 层    (MessagePort + zod schema 校验)
边界2: Orchestrator 与 Provider  (utilityProcess.fork + MessagePort + zod)
边界3: Provider 与系统    (sandbox + 仅通过 ProviderContext.secrets 访问敏感数据)
```

### 3.2 Provider Child 生命周期

| 事件 | 触发 | 动作 |
|---|---|---|
| Spawn | 首次调用该 Provider | `utilityProcess.fork()` 加载 Provider 实现 |
| Heartbeat | 每 5s | Provider Child 发心跳到 Orchestrator |
| Crash | 心跳超时 15s 或进程退出事件 | Orchestrator 标记 Provider 不可用、通知 UI、记录 crash日志 |
| Recycle | Provider 空闲 5min | 优雅退出释放资源 |
| Dispose | 应用退出 / Provider 被移除 | `dispose()` → process.kill |

### 3.3 第三方加载流程

```
用户点「Add Provider」
  → 选本地路径或 npm 包名
  → UI 弹 warning：「第三方 Provider 代码将作为子进程运行，crash 不影响浏览器，但请确认来源可信。v0.1 未做签名校验。」
  → 用户输入「我确认」
  → Orchestrator.forkProvider(providerId, packagePath)
  → fork 后调 Provider.initialize(ctx) 进行版本协商
  → 协商失败（apiVersion 不匹配）→ 拒载并通知 UI
  → 成功 → 注册到 Provider 注册表，UI 显示可用
```

> v0.1 不做签名校验；v0.4 引入 Provider manifest 签名 + 公钥 allowlist（与 NFR-SEC-07 对齐）。

## 4. 安全边界速查

| 边界 | 机制 | 防御对象 |
|---|---|---|
| 渲染进程 ↔ 主进程 | `contextIsolation: true` + `sandbox: true` + preload 暴露 typedInvoker | 恶意网页 → 主进程 Node API |
| 扩展 ↔ 主进程 | per-extension 独立 webContents + preload 注入 chrome.* + Backend 权限二次校验 | 恶意扩展 → 越权数据访问 |
| 扩展 ↔ 网页 | isolated world + `chrome.scripting` 仅白名单域名 | 恶意扩展 → 注入任意页面 |
| Provider ↔ 主进程 | utilityProcess.fork + ProviderContext 受限 API + namespace 隔离的 SQLite | 恶意 Provider → 主进程/其他 Provider |
| API Key 存储 | Electron `safeStorage`（OS DPAPI on Windows） | Provider 代码读到其他 Provider 的 key |

## 5. 错误传播策略

- **Provider 错误**：装箱为 `ProviderError`（含 `code` + `retryable`） → Orchestrator 决定重试或上报 → Renderer 收到 `IpcError` 翻译展示。
- **扩展崩溃**：webContents `render-process-gone` 事件 → Main 重启扩展 background page ≤3 次 → 超限则禁用并通知用户。
- **Tab 渲染崩溃**：`render-process-gone` → 展示错误页（TP3），用户手动 reload，避免死循环。
- **IPC 错误**：所有 handler 未经捕获的异常 → `IpcError('INTERNAL')` → 渲染层统一错误 toast。

## 6. 启动顺序

1. Main 启动，加载持久化状态（Settings/Bookmarks/History indexes）。
2. Main fork AI Orchestrator utility。
3. Main 创建主窗口（Renderer 进程），注入 preload。
4. Renderer 启动 React、加载 Zustand store 镜像、订阅 Main 事件流。
5. 用户首次触发 AI 调用 → Orchestrator fork 对应 Provider Child → `initialize()` 协商 → 进入可用状态。

> 启动时 **不** 预 fork Provider Child——按需启动减少冷启动开销与资源占用。

## 7. 日志策略

### 7.1 日志级别与用途

| 级别 | 用途 | 示例 |
|---|---|---|
| ERROR | 不可恢复的错误，需人工介入 | Provider 崩溃、IPC 超时、数据库写入失败 |
| WARN | 可恢复的异常，不影响主流程 | 第三方 Provider 版本不匹配、扩展 manifest 解析警告 |
| INFO | 关键生命周期事件 | 应用启动、窗口创建、标签关闭、扩展加载 |
| DEBUG | 开发调试用，默认关闭 | 每个 IPC 调用详情、每个令牌拼装细节 |

### 7.2 日志落盘位置

| 日志源 | 落盘路径 | 说明 |
|---|---|---|
| 主进程 | `%APPDATA%/Urchin/logs/main.log` | 应用级别的全部日志 |
| 渲染进程 | `%APPDATA%/Urchin/logs/renderer-<pid>.log` | 每渲染进程独立文件 |
| AI 编排器 | `%APPDATA%/Urchin/logs/orchestrator.log` | AI 调度与 Provider 通信日志 |
| Provider 子进程 | `%APPDATA%/Urchin/logs/provider-<id>.log` | 第三方 Provider 调试（仅 ERROR 级别落盘，隐私过滤） |

### 7.3 日志轮转

- 单文件最大 10MB，超过后自动轮转，保留最近 5 份。
- 日志文件自动清理超过 30 天的旧文件。
- 日志目录大小上限 500MB，超限时删除最旧文件。

### 7.4 日志内容约束

- **不得**记录敏感凭据（API Key、Token、密码）。
- 捕捉到 `ProviderError` 时，只记录 `code` 与 `message`，不记录 `cause` 中的原始 SDK 错误栈（可能含凭据）。
- 用户页面内容（URL、标题、正文）在 INFO 及以上级别不记录（隐私考虑），仅在 DEBUG 级别且用户主动开启调试模式时记录。
- 第三方 Provider 的日志输出（stdout/stderr）仅捕获 ERROR 级别，避免恶意 Provider 填充日志磁盘。

### 7.5 日志接口

```typescript
// packages/logger/src/index.ts
export interface Logger {
  error(msg: string, meta?: Record<string, unknown>): void;
  warn(msg: string, meta?: Record<string, unknown>): void;
  info(msg: string, meta?: Record<string, unknown>): void;
  debug(msg: string, meta?: Record<string, unknown>): void;
}

// 结构化日志格式
interface LogEntry {
  timestamp: string;          // ISO 8601
  level: 'ERROR' | 'WARN' | 'INFO' | 'DEBUG';
  module: string;              // 如 'tab-manager' / 'ipc-server' / 'orchestrator'
  message: string;
  meta?: Record<string, unknown>;
  // 自动附加
  processId: number;
  sessionId: string;           // 每次启动生成唯一 session ID，便于关联多进程日志
}
```
