# 内存占用归因与启动优化（2026-11-14）

## 结论

当前“约 1GB”的首要含义是 **6 个进程工作集的相加**，不是该浏览器独占 1GB 物理内存。Windows 对各进程分别计算共享的 Electron 映像、系统 DLL 等页；直接相加会重复计入。800MB 门禁仍按原公式判定，没有改成新口径，也没有放宽阈值。

另有一项可直接优化的固定开销：GenOffice 集成启动即加载 11,584,794 字节的嵌入包。主进程 V8 堆快照内有一份 22,960,196 字节的该包源码字符串，配合编译代码、对象等，使主进程 JS 堆常驻约 48MB。已延后到首次文档或资源操作时加载，保留完整编辑器与 AI 初始化路径；失败仍走原有查看器降级。

## 测量方法

- 当前依赖中的同一 Electron 43.8.8 二进制，独立临时 userData + data，串行启动，测量时没有并行构建／verify。
- 记录 `app.getAppMetrics()` 各 PID 工作集、私有提交量，主进程 `process.memoryUsage()`，各窗口 CDP JS 堆与 DOM 计数。
- 通过只读 `QueryWorkingSet` 枚举驻留页；依据 `Shared`、`ShareCount` 识别正在跨进程共享的页，并按映像文件完整路径 + 页偏移去重共享映像页。非映像共享映射仍全部相加，因此给出的是**驻留并集上界**，不是精确 PSS、不是 GPU 显存，也不代替既有门禁。
- 诊断实例带 `--expose-gc`，门禁本身不加该参数。不调用工作集裁剪、不以强制 GC 后的值替代门禁采样。单独的 GC 阶段只用于分辨暂存对象与仍被引用的对象。

参考：[Microsoft 工作集页结构](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-psapi_working_set_block)、[QueryWorkingSet](https://learn.microsoft.com/en-us/windows/win32/api/psapi/nf-psapi-queryworkingset)。

## 结果（MiB，显示值取一位小数）

| 场景 | 工作集合计 | 主进程 RSS | 主进程 JS 堆 | 驻留并集上界 |
| --- | ---: | ---: | ---: | ---: |
| 最小 Electron 空壳，1 窗口、4 进程 | 590.2 | 174.8 | 4.0 | 246.6 |
| 最小 Electron 空壳，3 窗口、6 进程 | 846.3 | 175.0 | 4.1 | 283.7 |
| 改动前 HEAD，补齐 GenOffice 构建产物，1 标签、6 进程 | 1031.8 | 254.9 | 48.1 | — |
| 优化前当前代码，10 主页标签、6 进程 | 1047.4 | 256.8 | 48.7 | 483.3 |
| GenOffice 按需加载后，10 主页标签、6 进程 | 1006.0 | 204.8 | 14.0 | 431.3 |

- 同进程数下，主进程 RSS 下降约 52MiB，JS 堆下降约 35MiB。全应用工作集合计的差值更小，其他进程／GPU 驱动也存在变化，不能将全部采样差值直接归为源码改动。
- 优化前，6 个进程中每个都有约 103～104MiB 的共享 Electron 映像页，单这一项工作集相加即约 620MiB。优化后 10 标签约 1006MiB 的原始合计中，共享映像按页去重后约 167MiB、独占驻留约 223MiB、共享非映像映射相加约 41MiB，得到约 431MiB 的保守上界。
- 10 个主页标签的 BrowserView 占位对象没有分别启动 10 个渲染进程；它们的 PID 为 0，实际 React 主页由主窗口渲染。该场景固定的 3 个渲染窗口是主界面、悬浮球与地址栏。
- 优化前一轮 1→10→1 标签：工作集增量约 25MiB，JS 堆约 48→49MiB；诊断 GC 后仍保留约 48MiB，符合固定模块持有。优化后诊断 GC 后主进程 JS 堆约 11MiB。额外连续 5 轮新增／关闭标签后，主进程 JS 堆为 12.4、13.2、12.6、12.8、12.9MiB；未观察到逐轮单调累积，最终 GC 后为 11.3MiB。
- 首次打开临时 HTML 文档后，GenOffice 模块才出现在 require 缓存，JS 堆约 49MiB；这是按需启用文档能力的开销，不代表模块被删除或功能被禁用。

## 对前一次基线结论的更正

前一次临时 worktree 只构建了浏览器 main／renderer／preload，缺少 `.gitignore` 中的 GenOffice out 产物，因此未加载编辑器重包，测得约 967.5MiB。该次对照不是完整功能等价的基线，不能拿它与完整构建的 1056.3MiB 直接判定本轮新增泄漏。

本次给旧 HEAD `49ffb67a` 接入与当前相同的 GenOffice 只读构建产物，再测得主进程约 48MiB JS 堆、工作集合计约 1032MiB，与优化前当前代码接近。该结果未发现近几轮邮箱／速记样式改动导致主进程 JS 堆暴涨的证据。

## 修改与边界

- 集成层支持延后加载；启动只注册宿主轻量通道，首次打开 GenOffice Home／文档或调用资源 API 时再初始化。
- Home 与剪藏使用按需 getter，避免在注册 IPC 时提前取嵌入包。初始化有单次尝试和缓存，避免重复通道注册。
- 提速后补首帧状态栏快照缓存与重放，并在子窗口尚未创建时就监听父窗口 show，防止早到的状态同步或首次显示事件被丢弃。采样对比以 6 个进程的完整场景为准，不把少创建一个窗口算作节省。
- 本次未合并／删除悬浮球或地址栏窗口，未改变三层进程结构，未更改 800MB 回归线。即使空壳三窗口原始工作集也超过 800MB，这说明需要基于明确口径重新讨论该门禁；本次不会自行修改产品验收标准。
- 这些结果针对主页和首次文档加载场景；不是对所有网页、大文档或长期会话作“没有内存泄漏”的保证。

## 最新验证

`pnpm run build` 与 `pnpm verify` 通过，桌面端 1850 项单元测试通过，覆盖率 71.38%。全量 43 例 E2E 中，40 通过、2 因外部依赖／认证条件不足跳过、1 内存门禁失败。10 标签三次工作集合计为 1000.2、990.6、990.2MiB，最小值仍高于原有 800MiB 回归线；该失败保留，不以共享页去重后的诊断数字替代验收结果。日志为仓库忽略的 `memory-build-verified.log`、`memory-verify-complete.log` 与 `memory-e2e-complete.log`。

## 复现

PowerShell：

```powershell
node scripts/diagnostics/memory.mjs apps/desktop "$env:TEMP/urchin-memory-report.json" --cycles=5
node scripts/diagnostics/memory.mjs apps/desktop "$env:TEMP/urchin-memory-document.json" --shell-only --open-doc
```

工具仅使用新建的临时档案。`--heap-snapshot` 可额外保存主进程 V8 堆快照；它可能很大，应留在本机临时目录。测试结束按本次创建的 PID 退出，不触碰安装版。原始样本保留于系统临时目录 `urchin-memory-*.json`，本机日志为仓库忽略的 `memory-*.log`。
