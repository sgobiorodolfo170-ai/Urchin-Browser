# ADR-010 · 邮箱模块选型与架构

> 状态：Accepted · 决策日：2026-09-24 · 关联：M25 / ML1 / ML2 / ML3 / ML4
> 影响范围：左侧栏新增入口、标签页体系新增 `urchin://mail`、SQLite 新增 `mail_*` 表、IPC schema 新增 `mail.*` 通道、package.json 新增 3 个运行时依赖
> 约束遵循：[新模块接入约束声明](../新模块接入约束声明.md)（全项通过）

## 决策

1. **ML1**：邮箱模块以 **imapflow（收）+ nodemailer（发）+ postal-mime（解析）三库组合 + 自建 React UI** 方案嵌入本项目，编号 **M25**。
2. **ML2**：IMAP/SMTP 引擎运行在**主进程**，UI 运行在**渲染进程**，二者经 M17 IPC（zod 双向校验）通信；MIME 解析（postal-mime）可在渲染进程侧执行以减少 IPC 传输量。
3. **ML3**：邮件数据存储复用 M8 SQLite，新增 `mail_accounts` / `mail_folders` / `mail_messages` 三表（version 2 迁移），表名以 `mail_` 前缀隔离，与其他模块表无外键关联；密码/凭据走 safeStorage 加密，不落 SQLite 明文。
4. **ML4**：左侧栏 pi 按钮下方新增「邮箱」按钮，点击创建/激活 `urchin://mail` 标签页——与 pi-web（`urchin://ai`）、settings（`urchin://settings`）模式一致。Mailspring（GPLv3）不纳入。

## 背景

用户指令：左侧栏 pi 按钮下边新增一个按钮模块：邮箱。搜索适合本项目的邮箱开源项目，作为一个模块嵌入本项目。

项目约束（AGENTS.md 项目声明）：生产级标准自 v0.1 全程适用；新模块接入须遵循 [新模块接入约束声明](../新模块接入约束声明.md)——不得对浏览器核心产生重大影响。

## 候选方案评估

经两轮调研（开源项目搜索 + 用户指定 5 项目逐项核实），评估如下：

### 候选 A：三库组合 + 自建 React UI（选定）

| 库 | 角色 | Stars | 许可证 | 维护 | TS 原生 |
|----|------|-------|--------|------|---------|
| imapflow | IMAP 收信（IDLE/QRESYNC/OAuth2） | 568 | MIT | postalsys 团队（EmailEngine 生产背书） | ✅ |
| nodemailer v10 | SMTP 发信 | 17.7k | MIT-0 | postalsys 团队 | ✅ |
| postal-mime | MIME 解析（Node + 浏览器） | — | MIT-0 | postalsys 团队（mailparser 继任者） | ✅ |

三库同属 postalsys 团队，API 哲学一致、升级节奏同步、生态协同无间。全 MIT 许可证，零 copyleft 风险。零原生编译依赖。

### 候选 B：Mailspring UI 提取（否决）

Mailspring（17.9k stars）是 Electron + React + TypeScript 邮件客户端，UI 开源（GPLv3），同步引擎为 C++（Mailspring-Sync，基于 Mailcore2）。

否决理由：
1. **GPLv3 传染**：若本项目非 GPL，嵌入 Mailspring UI 会强制本项目开源——属于许可证红线（§二.2 许可证红线），需架构性变更授权
2. **C++ 同步引擎**引入原生构建复杂度，与 T6「默认 TS」理念冲突
3. UI 与 Mailspring 自有 Electron shell 深度耦合，提取解耦工作量不低于自建
4. 旧版 React + 类组件风格，与本项目 React 18 + 函数组件 + Hooks 不一致
5. 主题与 M19 令牌不兼容，需重写样式

### 候选 C：SnappyMail 嵌入（否决）

用户初判为「SPA 纯前端 Webmail，无需后端，MIT」，经核实与事实严重不符：

| 用户描述 | 实际情况（README 核实） |
|----------|------------------------|
| MIT 许可证 | **AGPL v3**（最强 copyleft，网络服务即触发） |
| 纯前端 SPA，无需后端 | **PHP 7.4+ 必需**（mbstring 扩展），前端 JS 通过 PHP 后端 API 连接 IMAP |
| — | 前端用 KnockoutJS 3.5.1（非 React），是 RainLoop 的 PHP fork |

否决理由：AGPLv3 许可证 + PHP 依赖 + 非 React 前端，三重否决。

### 候选 D：@dyanet/imap 替代 imapflow（备选，未选定）

@dyanet/imap（v0.6.0，MIT，零依赖，strict TS）在零依赖与类型化错误体系上有优势，但成熟度不及 imapflow：

| 维度 | @dyanet/imap | imapflow（选定） |
|------|-------------|----------------|
| 成熟度 | v0.6.0，新项目 | 568 stars，739 commits |
| 生产背书 | 示例应用 | EmailEngine 商业产品 |
| Gmail labels | ❌ | ✅ X-GM-EXT-1 |
| 代理支持 | ❌ | ✅ SOCKS/HTTP CONNECT |
| 流式 fetch | ❌ | ✅ async iterator |
| 与 nodemailer 同团队 | ❌ | ✅ 生态一致性 |

对齐 AGENTS.md §九「维护度评估」，imapflow 在成熟度、生产背书、功能完整度、生态一致性四项上胜出。@dyanet/imap 作为备选（若 imapflow 依赖树出现安全/审计问题再切换）。

### 候选 E：react-email 撰写层增强（v0.2 起可选纳入）

react-email（19.8k stars，MIT）是邮件模板构建组件库，Editor 基于 TipTap（本项目已用 TipTap 2）。仅用于撰写环节，不侵入收信/列表架构。v0.2 撰写功能启动时可选纳入。

## 决策理由（方案 A）

1. **许可证干净**：全 MIT / MIT-0，零 copyleft，无需架构性变更授权
2. **架构完美契合**：引擎在主进程，UI 在渲染进程，IPC 走 zod 契约，存储复用 M8，与项目进程模型完全对齐
3. **零原生依赖**：三库均纯 JS/TS，无 node-gyp / 预编译二进制，与 T6「默认 TS」理念一致
4. **生态一致性**：三库同属 postalsys 团队，API 风格统一、协作无间、升级同步
5. **影响隔离**：对现有文件改动全部为追加性（7 个文件，零逻辑修改），新代码全部位于 `src/main/mail/` 和 `src/renderer/mail/` 独立目录（见 [新模块接入约束声明](../新模块接入约束声明.md) §一）
6. **功能可控**：按版本阶梯交付（v0.1 只读收信 → v0.2 发信 → v0.3 搜索/附件/OAuth2 → v0.4+ 规则/多账户）
7. **生产验证**：imapflow 经 EmailEngine 商业产品验证，nodemailer 是 SMTP 事实标准

## 否决方案理由汇总

- **B（Mailspring）**：GPLv3 传染 + C++ 引擎 + 解耦成本不低于自建
- **C（SnappyMail）**：AGPLv3 + PHP 依赖 + KnockoutJS 非 React，描述与事实不符
- **D（@dyanet/imap 替代）**：成熟度不足，作为备选保留
- **E（react-email 单独使用）**：仅邮件模板构建，非邮件客户端，不能替代完整方案，仅作撰写层增强

## 后果

### 正面

- 邮箱模块作为 M25 独立嵌入，复用 M8/M17/M18/M19 基础设施，不重复造轮子
- 全 MIT 许可证，无合规风险
- 三库生态一致，长期维护有保障（postalsys 团队持续维护）
- 分波次交付，v0.1 可在 1-2 周内交付只读收信

### 负面

- UI 全部自建（邮件列表/详情/撰写/账户配置），工作量较提取现成 UI 大
- imapflow 非 zero-dependency（有 postalsys 生态轻量依赖），但依赖树可控
- @dyanet/imap 的类型化错误体系（5 类错误）更契合项目 IpcError 装箱风格——imapflow 需自行包装错误类型

### 缓解

- UI 自建：按波次裁剪范围，v0.1 仅做收信列表+阅读，复用 M19 组件库
- 错误包装：在 `imap-client.ts` 封装层将 imapflow 错误统一装箱为 `IpcError`（`IpcErrorCode` 扩展 `MAIL_*` 系列）
- 成熟度：锁定 imapflow 精确版本，变更需经 §九 依赖引入审查
