二丫是顽童浏览器的原生 AI 助手：把用户目标转成可检查的行动，连接浏览器已有功能，并帮助用户比较选择、整理经验。用户保留目标、权限和重要操作的决定权。本立项建议先交付一个可信的小闭环，再逐步覆盖全部可接入模块。

版本：v0.4 评审草案。日期：2026年11月16日。下文“建议”是待评审的产品方案，不代表功能已经实现或工期已经承诺。

## 立项依据与当前基础

用户已经确定名称“二丫”，希望它成为浏览器的大脑，重点具备准确自动执行、主动决策辅助、有限且会整理的记忆，以及持续升级能力。这四项要求共同决定：二丫既需要模型，也需要权限、工具、执行状态、结果验证和记忆管理，单独接入聊天接口不能完成目标。

当前项目基于 Electron 和 Chromium，首版平台为 Windows。仓库已有标签、书签、历史、设置、下载、翻译、剪藏、笔记、邮箱、多工作区、GenOffice 和 pi 等功能与相关基础设施；这些模块的存在不等于已经向二丫开放。

当前 AI 助手入口确实仍是占位。源码中地址栏按钮无执行行为，设置页显示“AI 助手功能正在开发中”。2026年10月的整改已推进 AI 助手与 pi 的入口和设置分离，尚需清理旧命名上下游；二丫应作为独立产品能力建设，避免把 pi 会话、配置和权限直接当作二丫的数据与权限。

用户已确认二丫采用 `erya.*`。原 `ai.*` 是原生 AI 助手的预留命名，不归 Pi；现存 Pi 链路使用该名字是待清理历史引用。CUT-01 纳入立项范围与工作量：盘点调用方、协议、事件、存储、构建测试和文档，完成按归属迁出、废弃清理及安全数据迁移。技术验证接入真实模块前先通过其验收，详细清单见[06 系统技术架构设计](./06-二丫系统技术架构设计.md)。

## 产品目标与价值

建议首批面向浏览器中的个人知识工作：读资料、比较方案、整理收藏、形成笔记。用户不必掌握工具名称，只需说出目标；二丫负责提出步骤，说明依据，执行授权动作，并展示结果。

| 目标       | 用户能感受到的变化                 | 衡量方式               |
| ---------- | ---------------------------------- | ---------------------- |
| 准确执行   | “整理这几页”变成可核对的收藏或笔记 | 任务结果与预期状态比对 |
| 辅助决策   | 看见推荐理由、替代方案和信息缺口   | 来源支持率与用户复核   |
| 保留控制权 | 看见将读取什么、改变什么，并可停止 | 权限与撤销测试         |
| 有限记忆   | 有用偏好能保留，过期内容会整理     | 容量、遗忘与纠正用例   |
| 全模块融合 | 新功能可按统一方式加入二丫         | 工具覆盖清单逐项验收   |

“准确”不定义为永远不出错；它意味着范围明确、执行前检查、执行后核验，无法确认时如实说明。“仿生记忆”采用工作记忆、长期记忆、遗忘和压缩等工程机制，不作具有人脑或意识的承诺。

## 建议首版范围

首版闭环：用户选择网页 → 二丫提取带来源的内容 → 比较或形成计划 → 用户确认写入 → 创建书签或笔记 → 回读验证 → 保存经用户允许的记忆。

首版建议包含：独立入口、模型配置、当前或已选标签上下文、任务计划、细分授权、取消与失败提示、书签和笔记工具、结果核验、记忆查看纠正删除、容量上限、基本费用预算与评测记录。

A批最小闭环之外，速记、日历和邮箱列入B、C批当前计划。GenOffice、DeepSeek Harness、Pi的二丫交互只留痕远期立项。任意网站通用自动化、后台无限巡查、自动发信付款、跨设备记忆同步、自行改代码或升级权限不列入当前交付承诺。

## 权限与用户决定权

建议采用四档权限，并允许用户单独调整网站、工作区、工具和有效期。

| 档位        | 简单说明                                 | 典型行为         |
| ----------- | ---------------------------------------- | ---------------- |
| L0 对话     | 只使用用户主动提供的内容                 | 解释问题、写草稿 |
| L1 范围读取 | 读取用户明确选定的数据                   | 阅读这三个标签页 |
| L2 确认执行 | 写入前逐次显示并确认具体改动             | 新建这条书签     |
| L3 有限自主 | 在期限、次数、对象和预算内执行低风险动作 | 整理指定收藏夹   |
|             |                                          |                  |

建议首版开放 L0—L2；L3 先作为后续设计保留。发信、支付、不可恢复删除、凭据与权限调整等高风险操作，即使处于 L3 也逐次确认。网页文字、模型建议和历史记忆都不能自行赋予权限。允许读取与允许把内容发送给在线模型是两项分别管理的决定。

## 分阶段交付与退出条件

| 阶段          | 主要交付                                    | 退出条件                              |
| ------------- | ------------------------------------------- | ------------------------------------- |
| 前置准备      | 文档、原型、CUT-01与INT-00                  | 切割验收；工具与资源边界明确          |
| A批基础MVP    | 网页到书签或笔记、权限核验与有限记忆        | 原固定任务集和安全门禁通过            |
| B批速记与日历 | 笔记本、任务清单、笔记、文字便签与日历8工具 | S14—S16通过，并发和时间语义正确       |
| C批邮箱与协作 | 范围读取、草稿、确认发送、邮件转产物        | S08/S17通过，身份可靠、未知发送不重试 |
| 后续增强      | 主动建议、有限自主、自动记忆整理            | 独立评测与回退验证                    |
| 远期专项      | FUT-GO、FUT-DSH、FUT-PI                     | 届时另立项，当前不作为交付依赖        |

建议先做一次小规模技术验证，再按实际工作量估时；现阶段不承诺“几周完成全部二丫”。初学者应按“本阶段能演示什么”安排进度，避免同时开启所有模块。

## 资源与成本

产品负责人由用户承担：决定首批任务、隐私接受程度、每月预算并参加验收。开发者负责工具适配、权限与存储；测试工作覆盖正常结果和越权、取消、超时等异常。可以由同一人分阶段承担这些职责。

成本分为模型调用、测试调用、本地存储与开发维护。模型成本按实际输入、输出、工具轮次计算；先设置每任务和每月限额，再测真实任务平均费用。本地模型仍有设备、内存和维护成本，不等于无成本。具体价格与设备要求在模型选型报告核实后决定。

## 主要风险与开工条件

| 风险                         | 影响                              | 建议处理                                           |
| ---------------------------- | --------------------------------- | -------------------------------------------------- |
| 把全部功能一次做完           | 难以定位失败与交付                | 先两类写入工具，持续维护覆盖表                     |
| 网页内容诱导越权             | 误读隐私或执行错误动作            | 不可信内容与权限决策隔离                           |
| 记忆失真或过度保留           | 持续给出错误建议                  | 来源、纠正、失效期和级联删除                       |
| 与 pi 数据混用               | 权限与配置串扰                    | 独立命名、独立作用域、迁移测试                     |
| 旧 AI 命名与上下游未全面切割 | 配置误迁、调用绕行、Pi 与二丫耦合 | 将 CUT-01 作为 P0 前置任务，逐项清理并验证存量数据 |

开工前需确定 Muse 的具体产品、首版最重要的两三个任务、在线或本地模型的数据策略。其余可先按本文建议推进到可评审设计；正式实施时，将新增模块和必要的现有入口改动记录在 ADR 中，并遵循项目现有隔离与验证约定。

## 本轮范围与依赖

当前接入范围为速记页（笔记本中的任务清单、笔记、画布，以及本地日历）与邮箱页。A批先完成基础MVP，B批接入速记与日历，C批接入邮箱和跨模块协作；B、C均已纳入当前开发准备。GenOffice、DeepSeek Harness、Pi 与二丫的交互分别记为 FUT-GO、FUT-DSH、FUT-PI，当前只留痕待办，未来另行立项。CUT-01旧 `ai.*` 全面切割及原功能回归仍是近期前置任务，不随远期联动后置。

批次以验收推进，实施估时在接口缺口验证后填写，不承诺固定周数。任务、依赖、交付物和完成条件以04为准。

## DevTools接入的立项补充

二丫诊断指定网页在技术上可行。先利用用户提供的错误文本提供建议，再限定试验自动证据与验证；完整调试平台不进入首版承诺。现有原生F12已完成本机Win11验收，旧自研链路已退出，二丫需新建受控适配器。

DevTools接入按易到难分为DT-00手动报错解释、DT-01受控证据原型、DT-02按需Console、DT-03网络元数据、DT-04选定DOM/CSS、DT-05隔离样式预览与前后核验、DT-06二丫/Provider/工作区关联诊断。DT-00可在A批基础闭环后增加；自动采集作为C批后的D批限定试验，先做DT-01/02和DT-QA，后续能力在收益与安全门槛通过后逐项启动，不阻塞原A/B/C批。

采集证据原型遵循ADR-022按真实任务和对照结果决定投入；失败保留原生F12和手动解释能力，停止对应自动增强。GenOffice、DeepSeek Harness、Pi联动仍仅远期待办，关联诊断仅指二丫自身、共用Provider基础层和工作区的已授权元数据。
