# 01 · 愿景与定位

> 状态：Draft  · 日期：2026-07-27

## 1. 产品愿景

**让浏览器从「显示网页的容器」升级为「理解网页的智能工作台」**——同时不牺牲开发者对其行为的深度控制权。

两条腿走路：
- 给 **普通用户**：AI Side Panel 始终在侧，理解当前页面上下文，无需复制粘贴到 ChatGPT。
- 给 **开发者**：内置 DevTools 增强 + Chrome 扩展兼容 + 可脚本化 hooks，浏览器可作为编程工具而非黑盒。

## 2. 目标用户（v0.1-v0.3）

| 用户画像 | 核心诉求 | v0.1 满足度 |
|---|---|---|
| 知识工作者 | 快速摘要长文、抽取要点、对话式追问 | 中（依赖 Provider 配置门槛） |
| 前端/全栈开发者 | 在浏览器里调 LLM 写代码、看网络请求摘要、跑自定义 hook | 高（开发者友好定位直接命中） |
| AI 应用开发者 | 把浏览器当作 Agent 的「眼睛」——结构化抽取页面喂给下游 | 中（v0.2+ 提供 Page Context API） |
| 隐私敏感用户 | 数据不外泄、Provider 自选本地 LLM | 低（v0.3+ 接入 ollama 后才完整） |

> v0.1 不以纯普通消费者为目标——AI Provider 配置门槛决定了首版用户群偏技术。

## 3. 竞品对比与差异化

| 浏览器 | 核心 | Urchin 与其不同之处 |
|---|---|---|
| Chrome | 通用 + 生态霸主 | Urchin 默认内置 AI Side Panel 与 DevTools 增强，无需装扩展 |
| Edge | Chromium + Copilot 集成 | Urchin 不绑单一 LLM 提供方，Provider 插件化 |
| Brave | 隐私优先 + 广告拦截 | Urchin 隐私投入不及 Brave 极致，但以 AI 原生深度与 Provider 中立取胜 |
| Arc | 设计驱动 + 工作流改造 | Urchin 不依赖单一 UX 范式，强调可编程性与开发者控制权 |
| Wave/SigmaOS | AI 原生流派 | Urchin 走开源 + Provider 中立路线 |

差异化落脚点：
1. **Provider 中立**：用户自带 API key 或本地 LLM，浏览器不锁定 OpenAI/Anthropic。
2. **开发者可编程**：扩展系统兼容 Chrome MV3，v0.1 支持扩展加载与 API 子集，不依赖第三方生态。
3. **进程级安全边界**：Provider/扩展都跑在独立进程，crash 不带倒主浏览器。

## 4. 关键决策记录（D1-D8）

### D1 · 内核路线：Electron（否决 Tauri）

详见 [decisions/ADR-001-选Electron而非Tauri.md](./decisions/ADR-001-选Electron而非Tauri.md)。

**核心论证**：浏览器产品需深度介入页面层。Tauri 系统 WebView2 缺多进程标签沙箱、缺引擎版本控制权、`webContents` 级 API 受限——无法承载 AI 原生（页面内容抽取 + Side Panel 注入）与开发者友好（DevTools 增强 + 扩展 API）两个定位共同依赖的地基。

**否决方案**：Tauri（包小但本质是「带网页的应用」非浏览器）；Servo/Gecko（生态小）；自研内核（人年级工程）。

### D2 · 首版平台：仅 Windows

**核心论证**：首版 CI/构建矩阵简化为单平台，加快收敛。macOS/Linux 推到 v0.4+（基于 SemVer 次版本递进）。

**否决方案**：桌面三平台（首版工期 +50%、CI 复杂度 ×3）；移动端（需另选移动内核，非首版范围）；全平台（愿景宏大但 v0.1 难以收敛）。

### D3 · 差异化定位：AI 原生 + 开发者友好

**核心论证**：两条定位共同依赖 Chromium 内核层的深度控制权（`webContents` + preload + CDP），与 D1 选 Electron 互锁。

**否决方案**：隐私优先（与 Brave 正面竞争，且 Provider 中立已部分覆盖）；极致性能轻量（与 Vivaldi 竞争不占优）；纯 AI 单一定位（受众窄）。

### D4 · AI 进程隔离：utility process 分阶段迁移

详见 [decisions/ADR-004-AI进程隔离策略.md](./decisions/ADR-004-AI进程隔离策略.md)。

**核心论证**：主进程单线程事件循环是 Electron 致命伤，LLM 流式 token 拼装是 CPU 密集型，跑在主进程会肉眼可见卡 UI；Provider 插件代码可信度天然不可控，没进程隔离等于在主进程跑陌生人代码。

**分阶段**：v0.1 迁 LLM 调用 + Provider 插件到 utility；v0.2+ 迁上下文记忆/向量化。

**否决方案**：主进程内同驻（崩溃面 + CPU 阻塞风险）；外部 Sidecar（v0.1 工程税过重，留给 v1.0+ 本地 LLM 集成）。

### D5 · LLM 集成路线：Provider 插件机制

**核心论证**：项目不绑定任何 LLM 提供方，定义稳定契约；用户自带 API key 或本地 LLM。这是 Provider 中立产品定位的直接落地。

**否决方案**：云端单一 API（用户锁定）；纯本地 LLM（首版工程税过重）；不定义契约（生态混乱）。

### D6 · 扩展系统 API：Chrome 扩展兼容

**核心论证**：复用 Chrome 扩展生态，开发者迁移成本 0；「开发者友好」定位要求扩展生态兼容。

**代价**：需在 Electron 内模拟 chrome.* API 子集，与 Urchin 原生架构有耦合；v0.1 仅最小子集，v0.2+ 渐进扩展。

**否决方案**：Urchin 原生扩展 API（从零生态，与定位冲突）；双层 API（工程量最大，留作 v1.0+ 演进选项）。

### D7 · v0.1 范围：MVP 最小闭环（强隔离版）

详见 [decisions/ADR-008-v0.1范围与工期.md](./decisions/ADR-008-v0.1范围与工期.md)。

**核心论证**：4-6 周 MVP 最小闭环 + 强隔离 per-provider 子进程 = 实际 6-8 周工期。架构一次到位无技术债。

**v0.1 范围**：标签/导航/书签/历史/设置 + 扩展加载与基础 API 子集 + AI Side Panel demo（页摘要）+ DevTools 增强 demo + 1 个官方 Provider 接入。

**否决方案**：MVP + 扩展系统 + AI provider 抽象（8-12 周）；v0.1 全功能（含本地 LLM + 完整 DevTools 扩展，风险过高）。
