# 新模块接入约束声明

> 状态：已定稿 · 日期：2026-09-24 · 性质：约束性基线文档（对 AGENTS.md §一「上下文边界」/ §六「项目特化审查点」/ §九「质量护栏」的项目级明示与固化）
> 适用范围：每当有新功能模块加入 Urchin Browser 项目时，必须对照本声明逐项明确并留痕
> 关联：[AGENTS.md](../AGENTS.md) §一 总纲 / §六 Code Review / §九 质量护栏 / 项目声明 · [02-架构设计](./02-架构设计.md) · [04-模块全景](./04-模块全景.md)

## 〇、声明性质

本声明是 AGENTS.md「上下文边界」「自审」「不可逆操作审批」「质量护栏」原则在**模块接入场景**的项目级固化。性质为**填充细化**（§〇.3 允许），不新增架构性约定，不修改任何已有条款。

本声明确立一条核心准则：

> **新模块作为独立单元嵌入本项目，不得对浏览器核心功能产生重大影响。**

「重大影响」的判定标准：新模块的引入导致已有模块的逻辑被修改、已有数据结构被破坏、已有进程边界被穿透、已有安全基线被降低、已有验收信号失效——任一成立即构成重大影响，须停止并按 AGENTS.md §〇.4 请求授权。

## 一、影响隔离约束

### 1.1 追加性原则（Additive Only）

新模块对现有文件的改动**必须为追加性**（additive），不得修改已有逻辑行：

| 改动类型 | 允许 | 禁止 |
|----------|------|------|
| IPC schema 表追加新通道 | ✅ 追加到 `ipcSchema` 对象末尾 | ❌ 修改已有通道的 req/res schema |
| SQLite 迁移追加新 version | ✅ 追加新 `version: N` 到 `MIGRATIONS_*` 数组 | ❌ 修改已有 version 的 `up` SQL |
| 协议路由追加新 hostname | ✅ 追加 `if (url.hostname === 'xxx')` 分支 | ❌ 修改已有分支逻辑 |
| 侧栏追加新按钮 | ✅ 在现有按钮组内追加 `<button>` | ❌ 移动/重排/删除已有按钮 |
| App.tsx 追加新内部页判断 | ✅ 追加 `isXxxTab` 变量 + 渲染分支 | ❌ 修改已有 `isXxxTab` 的 URL 匹配规则 |
| main/index.ts 追加 handler 注册 | ✅ 追加 `import` + `registerXxxHandlers()` 调用 | ❌ 删除/修改已有 handler 注册 |
| package.json 追加依赖 | ✅ 追加到 `dependencies` | ❌ 修改/删除已有依赖版本 |

### 1.2 目录隔离原则

新模块代码必须**全部位于独立目录**内，不散落到已有模块目录：

```
apps/desktop/src/
├─ main/<module>/        # 模块主进程侧，全部代码在此目录
├─ renderer/<module>/    # 模块渲染进程侧，全部代码在此目录
└─ preload/              # 通常无需改动（见 §三.2）
```

例外：跨模块共享的工具函数可放入 `renderer/lib/` 或 `main/` 公共目录，但须注明来源模块。

### 1.3 失败隔离原则

新模块的任何异常**不得传播到浏览器核心**：

- 模块 crash → IPC handler 返回 `IpcError`，不传播到 Tab Manager / Window Manager
- 模块依赖加载失败 → 懒加载（dynamic import），不阻塞应用启动
- 模块 SQLite 表损坏 → 迁移事务回滚，不影响其他表（表之间无外键关联）
- 模块网络异常 → 标签页/面板显示错误状态，其他标签页正常

## 二、依赖引入约束

### 2.1 依赖审查清单（AGENTS.md §九 强制）

每个新引入的依赖须填写下表，未通过的依赖不得引入：

| 项 | 要求 | 验证方式 |
|----|------|---------|
| 包名验证 | npm registry 中存在且包名正确 | `npm view <pkg>` 确认 |
| 版本可达性 | 指定版本可安装 | `pnpm add <pkg>@<ver>` 干运行 |
| 许可证兼容性 | MIT / MIT-0 / Apache-2.0 / BSD | 检查 LICENSE / `npm view <pkg> license` |
| 维护度评估 | 活跃维护、有 stars/下载量背书 | GitHub 仓库活跃度检查 |
| 浏览器安全性 | 是否含 Node.js 原生模块 / postinstall 脚本 | 检查依赖树 |
| 原生编译 | 是否需要 node-gyp / 预编译二进制 | 检查 `binding.gyp` / `prebuild` |

### 2.2 许可证红线

| 许可证 | 可否引入 | 理由 |
|--------|---------|------|
| MIT / MIT-0 | ✅ | 最宽松，无传染 |
| Apache-2.0 | ✅ | 宽松，含专利授权 |
| BSD-2/3-Clause | ✅ | 宽松 |
| ISC | ✅ | 等同 MIT |
| LGPL | ⚠️ 需评估 | 动态链接可隔离，静态链接有传染风险 |
| GPL v2/v3 | ⚠️ 需用户授权 | copyleft 传染，可能强制项目开源 |
| AGPL v3 | ❌ 默认拒绝 | 最强 copyleft，网络服务即触发 |
| SSPL | ❌ 拒绝 | MongoDB 许可证，非 OSI 认证开源 |

> GPL/AGPL 类许可证的引入属于**架构性变更**（可能改变项目整体许可策略），必须按 AGENTS.md §〇.4 权限请求机制走完整 5 步流程。

### 2.3 依赖体积约束

- 单个新模块引入的运行时依赖**不超过 5 个**（不含已有依赖）
- 新增依赖的打包体积增量**不超过 10MB**（gzip 后）
- 不引入含原生编译的依赖（对齐 T6「默认 TS」理念），除非性能瓶颈经评估无法回避

## 三、进程与安全约束

### 3.1 进程归属声明

新模块必须明确声明代码运行在哪个进程：

| 进程 | 允许的代码 | 禁止的代码 |
|------|-----------|-----------|
| 主进程 (main) | 业务逻辑、IPC handler、SQLite 读写、网络 IO | CPU 密集计算（流式 token 拼装等） |
| 渲染进程 (renderer) | React UI、Zustand store、postal-mime 等浏览器安全库 | 直接 IMAP/SMTP 连接、文件系统操作 |
| utility 进程 | CPU 密集任务、Provider 子进程 | 直接操作 BrowserWindow |

> AGENTS.md §六 项目特化审查点：第三方代码（Provider/扩展）不得进入主进程。

### 3.2 IPC 契约约束

- 新模块的 IPC 通道必须以**模块域前缀**命名：`<module>.<action>`（如 `mail.account.list`）
- 所有通道必须在 `packages/ipc-contract/src/schemas/ipc-schema.ts` 的 `ipcSchema` 对象中定义 req/res zod schema
- handler 注册使用 `registerHandler(ipcMain, 'channel', ...)`，入参出参自动校验
- **preload 无需手动修改**：`createTypedInvoke` 自动暴露所有 `ipcSchema` 通道

### 3.3 安全基线（AGENTS.md §六 项目特化审查点强制）

| 项 | 要求 |
|----|------|
| 凭据存储 | 密码 / API Key / OAuth token → `safeStorage` 加密，不落 SQLite 明文 |
| 日志脱敏 | 密码 / token 不入日志；页面内容（URL/标题/正文）在 INFO+ 不记录 |
| 可序列化 | 跨进程状态必须可 JSON 序列化；Zustand store 禁止 Map/Set/Function |
| 渲染安全 | 外部内容（邮件 HTML / 网页）在 sandbox 渲染（iframe sandbox 或 DOMPurify） |
| 连接超时 | 网络 IO 须设超时（默认 30s），IDLE 须设心跳，防 hang |

## 四、存储约束

### 4.1 表命名隔离

新模块的 SQLite 表必须以**模块前缀**命名，与其他模块表无外键关联：

```
mail_accounts        ← 前缀 mail_
mail_folders
mail_messages
```

### 4.2 迁移隔离

- 新表在 `MIGRATIONS_MAIN` 数组中追加**新 version 号**（不修改已有 version）
- 迁移在事务内执行，失败则回滚，不影响已有表
- 若模块数据量大或隔离需求高，可申请独立数据库文件（如 `ai.db` 模式），须在 ADR 中说明

### 4.3 凭据隔离

- 模块的凭据（密码/token）使用 safeStorage，key 命名带模块前缀：`<module>-<entity>:<id>:<secret>`
- 凭据不通过 IPC 回传到渲染层（渲染层只持有非敏感配置）

## 五、UI 与主题约束

### 5.1 主题令牌一致性（M19）

- 新模块 UI 必须使用 M19 设计令牌（`bg-surface` / `text-text` / `border-border` 等 Tailwind class）
- 禁止硬编码颜色（`#ffffff` / `rgb(...)`）
- 暗色模式自动跟随 M19 ThemeProvider，无需模块自行处理

### 5.2 组件复用

- 基础 UI 组件复用项目 `renderer/components/ui/` 既有组件
- 新增组件须遵循 Radix UI Primitives + Tailwind CSS 技术栈，不引入第三方组件库

### 5.3 入口一致性

- 新模块通过侧栏按钮入口打开（与 pi / GenOffice / settings 模式一致）
- 点击按钮 → 创建/激活 `urchin://<module>` 标签页
- 标签页内由 React 组件渲染（BrowserView 占位）

## 六、测试与质量约束

### 6.1 覆盖率门槛（AGENTS.md §八.2）

新模块作为新增代码纳入覆盖率统计，须满足当前版本阶梯：

| 版本 | 整体单元覆盖率 | 新模块建议 |
|------|--------------|-----------|
| v0.1 | ≥60% | 工具类/纯函数 ≥90%，IPC 封装层 ≥80% |
| v0.2 | ≥65% | 逐版本提升 |
| v1.0 | ≥80% | 生产级标准 |

### 6.2 测试要求

| 层级 | 工具 | 要求 |
|------|------|------|
| 单元测试 | Vitest + 函数级 mock | 覆盖核心逻辑与边界 |
| 集成测试 | Vitest + :memory: SQLite | 模块内部各层协作 |
| E2E | Playwright `_electron.launch` | 至少 1 条核心路径（启动→操作→验收） |

### 6.3 质量门禁（AGENTS.md §九）

新模块代码须通过全部质量护栏方可合入：

- `pnpm typecheck` — TypeScript strict 模式
- `pnpm lint` — ESLint 9
- `pnpm test` — 单元测试 + 覆盖率门禁
- `pnpm e2e` — E2E 关键路径（涉及 UI/交互/主进程行为时）

## 八、接入检查清单（Checklist）

新模块开发前须逐项确认，全部通过方可启动编码：

- [ ] **§1 影响隔离**：对现有文件的改动均为追加性，零逻辑修改
- [ ] **§1 目录隔离**：代码全部位于独立目录
- [ ] **§1 失败隔离**：异常不传播到浏览器核心
- [ ] **§2 依赖审查**：每个依赖填写审查表，许可证全通过
- [ ] **§3 进程归属**：明确声明代码运行进程，网络 IO 不在渲染进程
- [ ] **§3 IPC 契约**：通道以模块域前缀命名，zod schema 已定义
- [ ] **§3 安全基线**：凭据走 safeStorage，日志脱敏，渲染 sandbox
- [ ] **§4 存储隔离**：表名带模块前缀，迁移追加新 version
- [ ] **§5 主题一致**：UI 使用 M19 令牌，无硬编码颜色
- [ ] **§6 测试覆盖**：覆盖率满足当前版本阶梯
- [ ] **§6 质量门禁**：typecheck + lint + test + e2e 全绿
- [ ] **§7 文档留痕**：ADR + 功能规划 + 模块登记 + 索引更新

## 九、例外与授权

若新模块因客观原因无法满足某项约束（例如需要引入 GPLv3 依赖、需要修改已有模块逻辑），必须按 AGENTS.md §〇.4 权限请求机制执行：

1. 停止修改
2. 向用户说明冲突点（哪条约束与实际情况冲突）
3. 提出修改方案与影响评估
4. 请求用户明确授权
5. 记录变更（在 ADR 中标注授权来源）

不得以「功能优先」「工期紧张」为由绕过约束。
